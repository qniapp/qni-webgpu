手順段階的に分割 → 各段でビルド & スナップショット確認

  1. mkdir src/render/ と空の src/render/circuit.rs / state_panel_layout.rs / state_panel_draw.rs 作成。render.rs に mod render { mod circuit; mod state_panel_layout; mod state_panel_draw; } を追加だけしてビルド確認 (空 mod のまま)。
  2. circuit.rs へ移動 — circuit_content_height + draw_circuit + draw_palette + draw_drag_preview。impl QniApp ブロックは新ファイル側にも書く (Rust は同じ struct の impl ブロックを複数ファイルに分散可)。cargo check → 既存テスト走らせて差分ゼロ。
  3. state_panel_layout.rs へ移動 — StatePanelLayout struct + state_panel_layout, grid_origin, dims_*, aspect_popover_layout, resize_handle_hit_rect, clamp_*。pub(super) struct → pub(crate) struct に visibility 引き上げる必要があれば調整。
  4. state_panel_draw.rs へ移動 — draw_state_vector + draw_aspect_popover + draw_state_minimap + draw_resize_handle_arc。state_panel_layout を use super::state_panel_layout::*; で呼ぶ。
  5. render.rs 本体を mod root 化 — pub use circuit::*; pub use state_panel_layout::*; pub use state_panel_draw::*; だけ残す (~30 行)。
  6. 最終確認: cargo check --target wasm32-unknown-unknown + Playwright snapshot で UI 差分ゼロを確認。

注意: 各ステップで commit を分けると、もし 1 つでもバグれば git bisect で問題箇所を特定しやすい。CLAUDE.md の「変更 → テスト → review → accept/reject」フローと相性が良い。

設計なぜ "layout vs draw" で切るのか

  • テスト容易性: layout 系は painter 不要の純粋関数。cargo test で叩ける (現状は wasm target のせいで叩けないが、将来 native target テストを追加する余地)。
  • 再利用しやすい: hit rect は app.rs 側の interaction でも、state_panel_draw.rs 側の描画でも使う。layout を別ファイルに切り出すと「描画とは別の責務」が明確になる。
  • 修正の局所性: 「色 / アイコン / 矢印を変えたい」→ draw 側のみ。「padding / 位置を変えたい」→ layout 側のみ。手を入れるファイルが一意に決まる。
  • circuit と state_panel の分離: 元々まったく別の UI 要素。混在してたのは歴史的経緯のみ。
