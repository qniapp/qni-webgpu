qni-webgpu · アーキテクチャ提案

デザインシステムのアーキテクチャ

Claude / Codex が Playwright で本物の見た目をピクセル単位で忠実に 検証できるよう、qni-webgpu のウィジェットを普通の HTML から カスタム要素として埋め込める仕組みを作る。 qni (../qni) のチュートリアル HTML と同じ流儀 (= <h-gate> タグを HTML に書くだけ) で qni-webgpu の ウィジェットが呼び出せるようにし、デザインシステムページとチュートリアルの両方を 同じ部品で書ける状態にする。

§ 01 なぜデザインシステムが必要か

現状の問題

  • docs/*-mock.html は HTML/CSS/SVG/JS でウィジェットの見た目を 近似している。フォントメトリクス・グリフアトラス・シェーダによる グラデーションの差分が残り、「モックでは合っているが実装で違って見える」が常につきまとう。
  • Claude / Codex がレビュー時に見るのはモック。実装直後の本物との見た目の乖離を Playwright で検証する手段がない (本物の wasm アプリは重く、特定ウィジェットだけを 切り出して比較する仕組みがない)。
  • 同じウィジェット仕様をモックと Rust 実装で二重に書く羽目になり、 食い違いが生じる。

解決ゴール

  1. 1 ソース原則: ウィジェットの見た目は qni-webgpu 内に 1 箇所だけ 実装し、デザインシステム / チュートリアル / 本番アプリで同じコードが描画される。
  2. 埋め込みやすさ: <h-gate> 1 行で 普通の HTML に挿せる (Qni のチュートリアル HTML と同じ書き味)。
  3. Playwright 検証可能: デザインシステムページを開いて任意の ウィジェットのスクリーンショットを取れば、本番アプリとピクセル単位で一致する。
  4. 段階的に拡張: 最初は静的 SVG アイコンから、シェーダ依存の 重いウィジェットは順次 wasm + キャンバス方式へ移行し、増やしていける。

§ 02 参考: Qni のチュートリアル埋め込み

../qni/html/h_gate.html 等のチュートリアル HTML では、普通の HTML に Qni 部品がカスタム要素として埋め込まれている。文中インラインに アイコンを置く軽い使い方から、全機能入りのミニシミュレータまで同じパターン。

使われ方の例 (qni チュートリアル本文より抜粋)

</p>

<!-- ブロックレベルに mini simulator -->

実装側の構造

  • TypeScript で HTMLElement を継承したクラス (packages/elements/src/h-gate-element.ts 等)
  • 中身は Shadow DOM + SVG アイコン (import hGateIcon from '../icon/h-gate.svg')
  • 単一の application.js が @qni/elements を読み込み、 各要素の @controller で登録
  • ページは <script src="./application.js"> を 1 つ読むだけで 全部品が使える

qni-webgpu はレンダリング方式が SVG ではなく WebGPU/egui である点が違うので、カスタム要素の中身は別実装になるが、外向き API (タグ名 + 属性) は qni の流儀に揃えるとチュートリアルの著者体験が共通化する。

§ 03 アーキテクチャ概要 — 2 階層のカスタム要素

カスタム要素の中身を「軽い Tier A: 静的 SVG」と 「重い Tier B: wasm + キャンバス」の 2 階層に分け、 用途に応じて使い分ける。同じウィジェットが両方を持つこともある (= SVG 版で軽量に 埋め込みつつ、必要なときだけ wasm 版に格上げ)。

design-system.html （リポジトリ直下）
ふつうの HTML、Geist フォント、カスタム要素を散りばめる
<h-gate></h-gate>                       ← Tier A (SVG)
<probability-display span="3"                   ← Tier B (wasm + canvas)
             probs="0.5,0,0,0,0,0,0,0.5">
</probability-display>
Tier A↓
Tier B↓
packages/elements/ Tier A
新規 TypeScript パッケージ（qni と同じく packages/ 直下）
  • h-gate, x-gate, ... のカスタム要素
  • Shadow DOM + 共有 SVG アイコン
  • 状態なし / GPU 不要 / 軽量
qni-webgpu ウィジェット専用モード Tier B
既存 wasm の別入口（リポジトリ直下の Rust クレート）
  • 1 キャンバスに 1 ウィジェット
  • 属性で状態を受け取る
  • 本番と同じ描画関数を呼ぶ（完全一致）

  widget: 'probability-display',
  span: 3,
  probs: [0.5, 0, ...],

両者は assets/icons/*.svg と src/shaders/*.wgsl を 1 ソースで共有

§ 04 Tier A: 静的 SVG ベースのカスタム要素

状態を持たない / アニメーションしない / GPU 計算を要しないウィジェットは SVG をそのまま Shadow DOM に流し込む薄いカスタム要素 にする。qni のゲートアイコンと同じ作り。最も軽く、文中インラインに散りばめる 用途で最強。

対象ウィジェットの例

  • パレット用ゲートアイコン: <h-gate>, <x-gate>, <cnot>, <probability-icon>
  • 状態を持たない、非インタラクティブな回路サムネイル
  • チュートリアル本文に挿す説明用ゲート列挙

HTML 利用例

<script type="module" src="/elements.js"></script>

  重ね合わせ状態が得られます。

実装 (TypeScript)

ts 
// packages/elements/src/h-gate-element.ts
import hGateIcon from '../../../assets/icons/h-gate.svg?raw';

export class HGateElement extends HTMLElement {
  connectedCallback() {
    if (this.shadowRoot) return;
    this.attachShadow({ mode: 'open' });
    this.shadowRoot!.innerHTML = `
      <style>
        :host { display: inline-block; width: 32px; height: 32px; }
        :host([size="sm"]) { width: 20px; height: 20px; }
        svg { width: 100%; height: 100%; display: block; }
      </style>
      ${hGateIcon}
    `;
  }
}
customElements.define('h-gate', HGateElement);

§ 05 Tier B: wasm + キャンバスベースのカスタム要素

GPU 計算を伴う、シェーダで描く、インタラクションがあるウィジェットは カスタム要素がキャンバスを作り、その上で qni-webgpu の wasm を ウィジェット専用モードで起動する。本番と完全同一の描画コードが走るので 忠実度は構造的に 100 %。

対象ウィジェットの例

  • Probability ゲート (コンピュートシェーダで周辺化)
  • ブロッホ球 (3D + 動く位相ニードル)
  • 振幅ディスク (状態ベクトル可視化)
  • ミニ回路エディタ (ドラッグ＆ドロップ操作が必要)

HTML 利用例

html 
<probability-display
  span="3"
  probs="0.5,0,0,0,0,0,0,0.5"
  width="32"
></probability-display>

<bloch-sphere theta="1.57" phi="0"></bloch-sphere>

<mini-circuit data-json='{"cols":[["H"],["Probability"]]}'>
</mini-circuit>

実装 (TypeScript) — 共通基底クラス

ts 
// packages/elements/src/wasm-widget-base.ts
import init, { start_widget } from '/widget.js';   // wasm-bindgen 出力（trunk dist から）

let wasmReady: Promise<void> | null = null;
function ensureWasm() {
  return wasmReady ??= init();
}

export abstract class WasmWidgetElement extends HTMLElement {
  protected canvas!: HTMLCanvasElement;

  abstract get widgetSpec(): {
    kind: string;
    width: number;
    height: number;
    params: Record<string, unknown>;
  };

  async connectedCallback() {
    if (this.canvas) return;
    this.canvas = document.createElement('canvas');
    this.canvas.style.display = 'block';
    this.appendChild(this.canvas);

    await ensureWasm();
    const { kind, width, height, params } = this.widgetSpec;
    this.canvas.width = width * devicePixelRatio;
    this.canvas.height = height * devicePixelRatio;
    this.canvas.style.width = width + 'px';
    this.canvas.style.height = height + 'px';
    start_widget(this.canvas, kind, params);
  }
}
ts 
// packages/elements/src/probability-display-element.ts
import { WasmWidgetElement } from './wasm-widget-base';

export class ProbabilityGateElement extends WasmWidgetElement {
  get widgetSpec() {
    const span = Number(this.getAttribute('span') ?? '1');
    const probs = (this.getAttribute('probs') ?? '')
      .split(',').map(s => Number(s.trim())).filter(n => !Number.isNaN(n));
    const width = Number(this.getAttribute('width') ?? '32');
    const height = span * 32 + (span - 1) * 20;          // = 52*span − 20
    return { kind: 'probability-display', width, height, params: { span, probs } };
  }
}
customElements.define('probability-display', ProbabilityGateElement);

Rust 側: ウィジェット専用モードの入口

rust 
// src/widget_entry.rs（配置は §06 を参照）
use wasm_bindgen::prelude::*;

#[wasm_bindgen]
pub fn start_widget(
    canvas: web_sys::HtmlCanvasElement,
    kind: &str,
    params: JsValue,
) -> Result<(), JsValue> {
    let spec: WidgetSpec = serde_wasm_bindgen::from_value(params)?;
    let renderer = match kind {
        "probability-display" => ProbabilityGateWidget::new(spec),
        "bloch-sphere" => BlochSphereWidget::new(spec),
        // ...
        _ => return Err(JsError::new(&format!("unknown widget: {kind}")).into()),
    };
    // 通常の eframe::start_web ではなく、ウィジェットだけを描く軽い egui ループを起動する。
    spawn_widget_loop(canvas, renderer);
    Ok(())
}

本番アプリの eframe 入口 (main()) と 同じ描画関数 (例: draw_probability_display(ui, &state)) を呼ぶ。違うのは「アプリ全体の クロムを描かず指定ウィジェットだけ描く」点と「シミュレーションは走らせず、属性から 渡された状態をそのまま使う」点だけ。

§ 06 パッケージ / ファイル構成

前提: 将来の整理（apps/tui/ を別リポジトリへ分離、qni-mcp を削除、apps/egui-web/ をリポジトリ直下に昇格して qni-webgpu として一本化）が済んだ後の構成。 Rust クレートが 1 個だけになるので apps/ 階層を外し、qni 本家と 同じく packages/ 直下に TypeScript パッケージを置く。

SVG ソース管理assets/icons/*.svg を唯一の正にする。Rust 側は include_bytes!、packages/elements/ は Vite で ?raw インポートで共有。
シェーダソース同じく src/shaders/*.wgsl を Rust 側で include_str!。ウィジェット専用モードで起動したウィジェットも同じシェーダを使うので自動共有。
配色 / 間隔の定数Rust 側の src/colors.rs が唯一の正。packages/elements/ 側で Tier A の SVG を書く際は、SVG 内に直接 16 進カラー値を埋め込む (Flexoki カラーをコメントで明記)。食い違いの検出は CI で src/colors.rs と SVG 内の 16 進カラー値を grep/diff で比較。
命名規則qni 本家と同じタグ名を採用 (<h-gate>, <x-gate>, <probability-display> 等)。qni のチュートリアル HTML をそのまま移植・流用しやすくする狙い。qni-webgpu は qni の後継として位置づけられているので、同一ページに qni と qni-webgpu の両方を混在させる運用は想定しない。
npm パッケージ名@qni-webgpu/elements または単に elements（モノレポ内で完結するので scope は任意）。ビルド成果物は elements.js を trunk dist 経由で /elements.js として配信。

§ 08 段階的ロードマップ

第 1 段階 — Tier A の最小スケルトン (H ゲートから)

  1. packages/elements/ パッケージを新規作成 (Vite + TypeScript)
  2. <h-gate> を SVG ベースの Tier A 実装で 1 個作る
  3. design-system.html をリポジトリ直下に作り、 Trunk.toml でコピー対象に追加。http://127.0.0.1:4174/design-system.html で開けるところまで
  4. Playwright で「ページを開いて <h-gate> の スクリーンショットが取れる」テストを 1 本
  5. このタイミングで packages/elements/ のビルド配管 / trunk への組み込み / SVG インポートのパターンを確立する

第 2 段階 — Tier A を残りのゲートアイコンに展開

  1. X / Y / Z / S / T / measurement / control / spacer などの SVG アイコンを assets/icons/ に揃える（本番 Rust 側も同 SVG を使うように移行）
  2. <x-gate>, <y-gate>, ... を順次追加
  3. design-system.html にゲートアイコンのカタログを追加

第 3 段階 — Tier B 第 1 号 (ブロッホ球)

  1. src/widget_entry.rs を新規作成、 start_widget(canvas, kind, params) を wasm-bindgen で公開
  2. Rust 側のブロッホ球の描画関数を「本番アプリから呼ぶ」「ウィジェット専用モード から呼ぶ」両方で使えるように切り出し
  3. packages/elements/ 側に WasmWidgetElement 基底クラスと <bloch-sphere> を実装
  4. Playwright で「theta/phi 属性を変えると ブロッホベクトルが対応する向きに描かれる」

第 4 段階 — Probability ゲート / 振幅ディスク / ミニ回路

第 3 段階で Tier B のパターンが固まったら、Probability ゲート (コンピュートシェーダ経由)、 振幅ディスク、ミニ回路エディタを順次追加。

第 5 段階 — チュートリアル / ドキュメントへの展開

同じ部品を使って docs/ 配下のチュートリアル HTML や、 将来的に学習教材的なページが書ける状態にする。Qni のチュートリアルから 移植・参考にできる構成になる。

§ 09 残っている設計判断

  • Tier B の wasm バンドルの重さ: start_widget 経由でも本番 wasm 全体が読み込まれるので 1 ページに 多数の Tier B を置くと重い。代替案:
    • (a) ウィジェット専用に小さい wasm を切り出す (バイナリを分ける)
    • (b) 同一ページ内では wasm を 1 度だけ初期化し、各キャンバスは同一インスタンス から多重描画する
    第 3 段階で 1 個動かしてから判断する。
  • egui の「1 アプリ = 1 キャンバス」制約: eframe は通常 1 キャンバスに 1 アプリ。複数キャンバスを同一 wasm から駆動するには eframe を介さず直接 wgpu の Surface を扱う必要があるかもしれない。 第 3 段階で検証する。
  • 属性から状態への対応付けスキーマ: probs="0.5,0,0,0,..." のような CSV / JSON / base64 / Quirk URL 形式の 4 案。CSV が一番読みやすいがウィジェットが増えると 厳しくなるかもしれない。data-json='...' 形式 (qni と同じ) も併用するのが 無難そう。
  • 素のカスタム要素を使うか、Lit / Stencil などのフレームワークを入れるか: 素のカスタム要素で書くか、Lit の薄いヘルパーを入れるか。qni は @github/catalyst を使っているが、qni-webgpu 側は依存を増やさず 素のカスタム要素で十分な気がする。
  • 本番アプリのアイコンを SVG に切り替えるか: 現状の本番アプリは egui の painter でゲートアイコンを描いている。 Tier A の SVG 化で 本番側も SVG アイコンに統一するのが 理想 (1 ソース化のため)。これは大きめのリファクタリングだが第 2 段階で扱う候補。
