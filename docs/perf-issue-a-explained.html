GPU に 5 往復
するか、1 往復で済ますか。

量子ゲートを 5 個並べた回路を 1 回シミュレーションするのに、 いま私たちは GPU と 5 回やりとりしている。 本当は 1 回で済む。これが Issue A のすべて。

§01 まず登場人物

ブラウザで Rust + WebGPU を動かすとき、コードは2 つの世界に分かれて住んでいる。

Fig. 1   ブラウザは セキュリティのため、Rust/Wasm が走る場所と GPU を直接叩く場所を別プロセスに隔離している。両者の間は IPC (プロセス間通信) でしかやりとりできない。
用語

encoder = 命令を書き溜めるノート。command buffer = ノートを綴じた完成品。queue.submit = それを GPU に提出する行為。

§02 なぜ「越える」のがコスト?

境界線を越えるたびに、毎回こういう手続きが走る:

Fig. 2   queue.submit 1 回の中身。問題はここで「中身がいくつ詰まっているか」を問わず、毎回このオーバーヘッドが乗ること。
アナロジー

宅配便で考えるとわかりやすい。荷物 1 個ずつでも 10 個まとめてでも、トラックを動かす燃料代は同じ。だったら 1 回の便にまとめたほうがいい。

§03 いま起きていること

StateVectorCallback::prepare の中、recompute ブロックではゲート 1 個ごとにこうしている:

Fig. 3   ループの中で encoder を作って即 submit しているので、ゲートの数だけ往復が発生する。実際の計算 (黒) よりも往復 (赤) のほうが時間を食うことすらある。

§04 どう直すか

アイデアは単純。ノート (encoder) を 1 冊だけ用意して、ゲート全部の命令をそこに書き溜めてから、最後に 1 回だけ提出する。

Fig. 4   encoder をループの外で 1 つだけ作る。ループ内では begin_compute_pass → dispatch → end を繰り返すだけ。submit はループの後で 1 回。

§05 Before / After

Before — 現状ゲートごとに submit

// gpu.rs:2126–2289
for op in &self.sim_ops {
    let mut encoder = device
        .create_command_encoder(...);
    {
        let mut pass = encoder
            .begin_compute_pass(...);
        pass.set_pipeline(...);
        pass.dispatch_workgroups(...);
    }
    queue.submit(Some(encoder.finish()));
}

After — 改善案1 回にまとめる

// 提案
let mut encoder = device
    .create_command_encoder(...);
for op in &self.sim_ops {
    {
        let mut pass = encoder
            .begin_compute_pass(...);
        pass.set_pipeline(...);
        pass.dispatch_workgroups(...);
    }
}
queue.submit(Some(encoder.finish()));

§06 大事なところ — 順序は崩れない

「ゲート 1 の結果を ゲート 2 が使う、これ大丈夫?」と思うかもしれない。大丈夫。

WebGPU は同じ encoder の中に書いた compute pass は、書いた順番で実行されることを保証している。間に submit を挟む必要はない。間に挟む submit は同期のためではなく、単に「ここまで提出」という区切りでしかない。

補足

ゲート間のメモリ依存も WebGPU が automatic に解決する (memory barrier を内部で挿入する)。なので「明示的に同期」が必要な場面は基本ない。

§08 まとめ

Issue A の本質:
「GPU との会話は提出回数でコストが決まる。中身の量ではない」。
だから提出は最後にまとめて 1 回。

変更範囲: gpu.rs の recompute ループ周辺、約 50 行。 shader には触らない。スナップショットも変わらない (描画結果は同じ)。

リスク: 低。WebGPU の仕様上、同じ encoder 内の pass 順序は保証されているため、振る舞いは現状と等価。
