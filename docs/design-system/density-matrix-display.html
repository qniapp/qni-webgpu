密度行列表示ブロック

span 内の量子ビットを測定せずに、局所的な混合状態 (reduced density matrix) ρ = Trrest(|ψ⟩⟨ψ|) を可視化する密度行列表示ブロック (表示ブロック の定義は AGENTS.md 用語集と design-system §01 参照)。 振幅表示ブロックが α = re + i·im 1 本を 2span セルで描くのに対し、本表示ブロックは ρij の 2span × 2span 全成分 を行列状に描く。 対角成分は 各測定結果の確率 P(|i⟩) = ρii、非対角成分は coupling / coherence ρij (絶対値 = 大きさ、偏角 = 相対位相)。 span 上限は 8 量子ビット (Quirk DensityMatrixDisplay と同じ。216 = 65 536 セルの正方行列、vec2<f32> で 512 KB を GPU storage で扱う上限)。 配色 (blue-200 fill / blue-400 disk border / tx-2 outline / tx needle) は 振幅円 プリミティブに従い、振幅表示ブロック / 状態ベクトルパネルと完全に揃える (Quirk の #3F3 / #040 緑系は Flexoki に馴染まないため不採用)。 Quirk の DensityMatrixDisplayFamily (src/gates/DensityMatrixDisplay.js) と MathPainter.paintDensityMatrix を Flexoki + WebGPU + Qiskit Aer 二系統経路へ移植する仕様書。

★ 批評 · 全体所見
「N×N 行列を 1 widget に詰める」根本的なスケーラビリティ問題が § 05 表に押し込まれている

Flexoki Light 準拠、振幅表示ブロックとのセル描画統一、二系統経路 (WebGPU 内部 + Qiskit Aer) を併記した網羅性は probability-display.html / amplitude-display.html と同等で、仕様としての完成度は高い。 ただし本表示ブロックの固有の難しさは 「セル数が 22 × span = (振幅表示ブロックの 2 乗) で爆発する」こと。 span 1 で 4 セル、span 2 で 16 セル、span 4 で 256 セル、span 8 で 65 536 セル。同じ span でも振幅表示ブロックは 2span セルなので、密度行列表示ブロックは 常に振幅表示ブロックの 2 乗倍のセルを持つ。 これが「span 上限 8」(振幅は 16) の根本理由だが、§ 05 ジオメトリ表に cellPx = 1.69 px と数値だけが並んでおり、「N × N matrix を視覚化することそのものの限界」がフレーミングされていない。span 8 の 65 536 セルを 432 × 432 px 正方形に詰めた heatmap は production の標準描画だが、視認できる構造は対角ピーク 1 つだけになり、もはや「行列」と呼べない情報密度になる。

「対角 = 確率、非対角 = coherence」という 2 つの異なる意味を同じセル形状で描く判断も本表示ブロックの固有問題で、§ 06 で 「対角も非対角も outline 円 + magnitude disk、対角だけ needle 省略」と統一されている。 これは振幅表示ブロックとの語彙統一として優れているが、対角の ρii = 確率 と非対角の ρij = coupling は物理的に別の量 (確率は [0, 1]、coupling は複素数で大きさ ≤ 0.5) で、同じ「半径 = mag」表現にすると対角の disk は最大 1 まで膨らみ、非対角は最大 0.5 までと視覚的スケールが構造的に対角優位になる。Quirk は対角を probability bar、非対角を disk と形を変えて区別していたが、本仕様はこれを統一する選択をしている。利点 (sibling との学習コスト低減) は明示されているが、欠点 (対角 = 大きい disk が視覚的に支配し非対角の coherence が脇に追いやられる) は仕様内に書かれていない。

影響度の大きい改善候補 (各論は本文中の批評ブロックに展開)
  1. span 7〜8 の「heatmap が production 標準になる」事実をフレーミング — 振幅表示ブロックでは mock 限定だった heatmap が、本表示ブロックでは production 標準。「行列ではなく濃淡で全体像を見るモード」と明示し、cellPx ≥ 3 の outline + disk モードと意味的に区別する (§ 02 / § 05 / § 06 参照)。
  2. 対角 vs 非対角の視覚スケール不均衡を明示 — 対角 disk は半径 ∝ ρii ∈ [0, 1]、非対角は |ρij| ≤ 0.5。同じ表現に統一する trade-off (Quirk は形を変えて区別していた) を § 06 冒頭で言語化 (全体所見 / § 06 参照)。

  4. operation 前後の diff 表示の余地 — 量子操作後の ρ の変化 (どの coupling が増減したか) は単一スナップショットでは読めない。「直前の ρ との差分表示モード」が将来 価値を持つ可能性 (§ 06 後半 / § 11 参照)。
  5. § 05 / amplitude-display.html § 05 の placement モデル共有化 — wide gate (cols > 1) の placement / URL round-trip / 幾何交差判定は両仕様で 1:1 同型。共通仕様 wide-gate-placement.html へ抽出する余地 (§ 05 参照)。
  6. 二系統経路 (WebGPU 内部 / Qiskit Aer) のスイッチ UI 仕様が無い — § 10 表に推奨用途が書かれているが、ユーザが UI で経路を選ぶ手段が定義されていない。ExecMode 設定との連動 (§ 10 参照)。

★ 批評 · § 01 概要
「振幅表示ブロックとの差別化」が「行列か否か」だけに集約されている

lede と § 01 で「振幅表示ブロックが 2span セル、本表示ブロックが 2span × 2span セル」と数値的差分が示されるが、 「なぜユーザが密度行列表示ブロックを必要とするか」が「混合状態 / もつれを 1 枚で読み取れる」の 1 行に圧縮されている。 実際の使い分け軸は (a) span 内が span 外と entangled かを判別したい (純粋状態なら振幅表示ブロックで十分、混合状態なら密度行列表示ブロックが必要)、 (b) coupling (非対角) のパターンから entanglement の構造を見たい (例: Bell の ρ03, ρ30 = 0.5 という対角四隅パターンが entanglement の特徴)、 (c) Tr(ρ²) = purity で混合度を定量化したい の 3 点。

改善案: § 01 末尾に 「振幅表示ブロックでは見えない情報 = 何か」を 1 表で示す。Bell state を例に「振幅表示ブロック on q0 = |+⟩ に見える / 密度行列表示ブロック on q0 = I/2 (最大混合) と見える」の対比を入れると、両表示ブロックの使い分けが学習者に明確に伝わる。 Quirk は両 display を並べて見比べることを暗黙に推奨しているが、qni-webgpu の本仕様で明示的に定義する価値がある。

span 7〜8 の heatmap モードが「production の標準描画」だと強調されていない

§ 02 で span 7 (cellPx 2.94) と span 8 (cellPx 1.69) は heatmap モードへ切り替わる、と書かれているが、 「production の標準描画として heatmap が必要」と注記で済まされている (§ 05 表に同じ注記)。 これは振幅表示ブロック (mock 限定 heatmap) との決定的な差で、 本表示ブロックの span 7〜8 を選んだユーザは「行列を 1 枚で見る」という当初の期待 (§ 01) を heatmap では満たせない (outline 円 / disk / needle がすべて消え、濃淡だけが残る)。

改善案: § 02 の見出しレベルで「span 1〜6 (matrix モード) と span 7〜8 (heatmap モード)」と並列の章立てにし、heatmap を 「行列ではなく濃淡で全体像を見るモード」として明確に別 widget 扱いにする。 現状の構成は「同じ密度行列表示ブロックが、span が大きくなったら自動でモード切替する」だが、ユーザは span を 6 → 7 に上げたとき本体の見た目が断絶する。これは UX 上「壊れた」と誤解されやすい。 Quirk も同じ behavior だが、ユーザに「これは設計判断」と伝えるドキュメントが本仕様の役目。

「純粋状態 vs 混合状態」の見た目セクションが Bell と I/4 だけで構造が伝わらない

本セクションは 純粋 (Bell) と 最大混合 (I/4) の 2 例を並べているが、これらは両極端で「中間の混合状態」が示されていない。 実回路では 3/4 純粋 + 1/4 混合 のような中間状態が頻出し、ユーザは「対角と非対角の disk 大きさの比」から混合度を読み取る必要がある。 改善案: (a) 純粋 (Bell) / (b) 50% 混合 / (c) 最大混合 (I/4) の 3 段階を並べ、各 widget の下に Tr(ρ²) = purity の数値を補助テキストで併記する (1.0 / 0.625 / 0.25 のように単調減少が見えると教育的)。

純粋状態の判別: rank=1 という構造が視覚化されていない。 純粋状態 |ψ⟩⟨ψ| は rank 1、混合状態は rank > 1 という代数的事実は密度行列表示ブロックの主要な情報量だが、本仕様の disk 表現ではこの構造を直接読めない (rank は固有値分解しないと出てこない)。 Quirk と同じ制約だが、qni-webgpu 独自の改善案として「純粋なら disk pattern が 1 つの outer product (列ベクトル × 行ベクトル) で書ける」という構造を hover で示唆する余地がある。

§ 03 パレットアイコン (mini preview)

パレットに並ぶ DensityMatrixDisplay アイコンは 40 × 40 px の静的 mini preview。 2×2 行列 (= span 1) を 純粋 |+⟩⟨+| の密度行列 として描く: 4 セルすべてに 0.5 半径の magnitude disk + outline 円、非対角 2 セルだけは追加で真上 needle (実数なので位相 0 = 真上)。 「対角 / 非対角ともに disk、非対角だけ needle が立つ」という本表示ブロックの統一されたセル描画を 1 アイコン内で提示し、密度行列特有の行列 (matrix) 形状を視認させる。 アイコン自体の外側に四角枠は描かず、4 つの円だけで密度行列表示ブロックだと分かるようにする。円周の外端はセル境界から 1.5 px だけ内側に置き、hover 枠と重ならない範囲で最大化する。 ホバー時は外側のホバー枠だけ表示 (静的なので個別 cell ポップアップは出さない)。

本表示ブロックのアイコンは 2×2 行列 (span 1 の |+⟩⟨+|) で 4 つの disk を並べ、密度行列特有の行列形状を最初から提示する。 これは振幅表示ブロック (1 セル) や確率表示ブロック (4 行ガウシアン) より意図が明確で、設計判断として優れている (probability-display.html / amplitude-display.html § 03 の批評で「アイコンと配置後の形状ジャンプ」を問題視したのと対照的)。

§ 06 セル描画モデル (全セル統一、対角は needle のみ省略)

Quirk の paintDensityMatrix (src/draw/MathPainter.js) を Flexoki + 振幅表示ブロックの視覚言語へ移植する。 対角 / 非対角ともに同じ「outline 円 + magnitude disk」レイヤで描き、対角だけ needle を省くのがポイント。これにより:

  • 対角セル ρii = 実数の確率 P(|i⟩) ∈ [0, 1]。 outline 円 + magnitude disk の 2 層で描く。 disk 半径 = ρii × inner_radius (= P × inner_radius)、半径ゼロ (P = 0) なら disk を描かない。 needle は描かない: 対角は常に実数 (位相 0) なので needle が真上を向くだけになり情報量を持たず、視覚的ノイズになる。Quirk の Probability square (下から上に伸びる塗りバー) は採用せず、非対角と同じ disk 表現で統一する (対角セルだけは確率の値を disk の半径として読む)。
  • 非対角セル ρij (i ≠ j) = 複素数の coupling。 振幅表示ブロックと同じ outline 円 + magnitude disk + disk 境界線 + phase needle の 4 層で描く。 mag = |ρij|、phase = arg(ρij)。 disk 半径 = mag × inner_radius、needle 方向 = (−sin(phase), −cos(phase)) で真上が phase 0。 境界線 / 配色は振幅表示ブロックの規約に従う (amplitude-display.html § 06 と完全共有)。
  • Hermitian 性 — 密度行列は ρij = conj(ρji) なので、上三角と下三角は位相が反転した対称。表示としても自動的に左下と右上の needle が鏡像になるため、ユーザーは行列の片側を読むだけで全体が読める (Quirk と同じ視覚言語)。対角は実数 (虚部 0) なので Hermitian 性も自動的に満たされる。
(1) back fill — セル背景。通常時は bg (#FFFCF0)。drag preview 中は matrix 外周のみ purple-600 に差し替え、内部の cell 描画 (outline / disk / needle) は通常時のまま

// (Quirk DensityMatrixDisplay.js:107-124 と等価、qni 内部で GPU compute pass として組む)
for row in 0..n:

本仕様は対角も非対角も「outline 円 + magnitude disk」で統一し、disk 半径は対角なら ρii = P、非対角なら |ρij|。 この統一は振幅表示ブロック / state panel との語彙共有として優れているが、物理的には:

対角は P / log の 2 行、非対角は val / mag / phase の 3 行と異なる構造。 amplitude-display.html § 08 で指摘されているのと同じ「popup の高さが状態依存で変動する」問題が本表示ブロックでも発生する (cell hover で対角 → 非対角に移ると popup が成長する)。 改善案: 対角でも 3 行構造にして P / phase = 0° / mag = √P と書く (情報量は重複するが popup レイアウトが固定される)、または非対角でも 2 行に圧縮 (val / phase のみ、mag は val から導出可能)。

対角の log dB と確率表示ブロックの log dB の意味が違う: 確率表示ブロックの popup の log = (log10(p) × 10).toFixed(1) dB は線形バー上の確率の dB 表現。 密度行列表示ブロック対角の同じ log dB は密度行列の対角要素の dB だが、これは部分トレース後の確率であり、確率表示ブロックの値と意味的に異なる場面がある (確率表示ブロックは marginalize 後の確率、密度行列対角は reduced density matrix の対角)。同じラベル log でも、span 内が span 外と entangled かどうかで意味が変わる。 改善案: 対角の popup ラベルを log P と明示する / 「reduced (span 内のみ)」を補足表記に入れる、など意味の違いをユーザに伝える。

Tr(ρ²) = purity が popup / 補助テキストに出てこない

本表示ブロックの本質的な情報量は 純粋度 (purity) = Tr(ρ²) ∈ [1/n, 1]。1 なら純粋、1/n なら最大混合。 現状の cell hover popup は個別 cell の値しか出さず、行列全体の purity / entropy / rank などのaggregate な指標が見えない。 改善案: matrix 全体に hover した時 (cell に当たっていない時) に widget 下部に Tr(ρ²) = 0.625 のようなscalar summaryを出す、または常時 widget 下の補助テキストに表示する。Quirk は printParagraph でこれを下に表示しており、qni-webgpu でも採用する価値が高い。

§ 10 Qiskit / GPU 実装メモ (二系統経路)

密度行列表示ブロックは 2 つの計算経路を持つ: (a) WebGPU 内部実行 (qni 単体で動く既存経路、振幅 / 確率表示ブロックと同じ scheme) と (b) 外部 Qiskit Aer 経路 (qiskit-backend からの結果を受け取る経路、apps/qiskit-backend と統合)。 どちらも本番 UI 経路では GPU → CPU readback しない規約に従い、結果を GPU storage buffer に置いて render shader が直接 sample する。

(a) WebGPU 内部実行 (qni 単体、振幅表示ブロックと同パイプライン)

Quirk の densityDisplayStatTexture (DensityMatrixDisplay.js:44-71) を WebGPU compute pass 列へ移植:

  1. Control select + cycle — controls を満たす要素だけ詰めて span subspace を head に持ってくる (Quirk CircuitShaders.controlSelect + cycleAllBits)
  2. amplitudes → couplings — Quirk AMPLITUDES_TO_DENSITIES_SHADER と等価な compute kernel: ρij(rest) = ψi,rest · conj(ψj,rest) を各 rest 値ごとに計算し、出力 buffer に vec2<f32> で書き込む。要素数 = 2rest × 2span × 2span
  3. Partial trace (sum-fold) — rest 量子ビットについて sumFold で畳み込み、最終的に ρ: vec2<f32>[2span × 2span] の縮約密度行列が得られる
  4. unity 正規化 — unity = Σ ρii.real を reduce、ρ /= unity を全要素並列で適用 (Quirk densityPixelsToMatrix と等価)
  5. measured-bit decoherence — controls / lowering で得た is_measured_mask を渡して、(row ^ col) & mask != 0 な非対角を 0 に潰す compute pass (Quirk decohereMeasuredBitsInDensityMatrix と等価)
  6. render shader — 出力 storage バッファを fragment shader が直接 sample。outline / disk / needle / 外枠はすべて fragment shader 内の SDF で描く (振幅表示ブロックの amplitude_result シェーダと同型)

(b) 外部 Qiskit Aer 経路 (apps/qiskit-backend、実装済み)

外部 GPU 実行では、Web 側が配置済み Density Matrix 表示ブロックを outputs.densities に列挙し、qiskit-backend が QuantumCircuit.save_density_matrix(qubits, label=...) で縮約密度行列を保存する。応答は densities 配列で返り、各項目は gate_id / span / cells / unity を持つ。cells は行優先の [re, im] 配列で、サイズは 2span × 2span 複素数。

  • バックエンド側 — contract.py が outputs.densities を検証し、span 1〜8 / 最大 16 件を受け付ける。runners.py は各列のゲート適用直後に save_density_matrix を挿入し、densities[].cells へ変換する
  • Web 側要求 — apps/web/src/app/external_gpu/density.rs が {"gate_id", "column", "span", "base_bit"} を生成する。Control と同じ列に置いた Density Matrix 表示ブロックは、外部契約へ control_mask / control_value を追加するまで拒否する
  • Web 側描画 — 応答 JSON を Float32Array 相当の連続値へ平坦化し、DensityMatrixDisplayCallback が density_output / density_meta GPU バッファへ queue.write_buffer で転送する。転送後の描画は (a) と同じ DENSITY_RENDER_SHADER が担当する
  • 測定済み wire の注意 — 現在の外部経路は Aer の保存結果をそのまま表示する。測定済み wire の非対角を WebGPU 内部実行と完全一致させるための追加 decoherence pass は今後の改善候補

経路 (b) の decoherence 未実装が「今後の改善候補」のまま放置

本文に「測定済み wire の注意 — 現在の外部経路は Aer の保存結果をそのまま表示する。測定済み wire の非対角を WebGPU 内部実行と完全一致させるための追加 decoherence pass は今後の改善候補」と書かれているが、 これは経路 (a) と (b) で同じ回路に対して異なる行列が表示されることを意味する。 ユーザは「同じ Bell state なのに、Local モードと Qiskit モードで非対角の値が違う」という再現性の破れに遭遇する可能性がある。 改善案: (1) 経路 (b) でも qni 側で post-process decoherence を適用する compute pass を追加する、または (2) 本仕様に「measured wire を含む場合は経路 (a) のみサポート」と明示制約を入れて経路 (b) で reject する。 現状の「今後の改善候補」は決定保留であり、ユーザに混乱が生じる前に方針を固める価値がある。

レイテンシ「backend RTT 依存 (典型 100 ms〜数秒)」の UX 影響が定量化されていない

§ 10 表に「(b) レイテンシ: backend RTT 依存 (典型 100 ms〜数秒)」とあるが、density 表示ブロックが drag / resize 中にこのレイテンシで動くと「ハンドル動かしてから数秒後に描画が更新される」という体験になる。 振幅 / 確率表示ブロックの (a) WebGPU 経路は frame 内 (16 ms 程度) で完結するので、表示ブロック族全体の体感速度が経路選択で激変する。 改善案: drag / resize 中は強制的に経路 (a) (= placeholder + 暫定描画) を使い、操作完了後に (b) で精密な値を取り直す、というhybrid モードを仕様化する。
