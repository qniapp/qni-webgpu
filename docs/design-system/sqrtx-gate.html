√X ゲート (√NOT)

単一量子ビットへ (√X)2 = X となるユニタリ変換を適用する平方根 NOT ゲート。 回路エディタ上では 40 × 40 px の cyan-400 角丸正方形に、Geist Regular 由来の √ と X を合成した字形を中央配置する。X ゲート本体の円形とは分け、H / Y / Z / S / T と同じ 1 量子ビット操作ゲートの見た目を継承する。

★ 批評 · 全体所見
「multi-character 字形」を採用する初のゲートとしての特殊性が議論されていない

ユニタリゲート chrome (40 px 本体 + 56 px ピッチ + cyan-400 + paper グリフ + drag preview = purple-600) は h-gate.html の全体所見と同じ批判 (ページ間で内容が重複し、親仕様の抽出が望ましい) がそのまま当てはまる。 ここでは √X 固有の論点に絞ると、本ページは H / X / Y / Z が「単文字グリフ」で揃う Pauli 族の中で初めて multi-character (√ と X の合成) 字形を採用するゲート。これは仕様横断で 1 つの転換点であり、後続の RX / RY / RZ / QFT など複数文字グリフのゲート群が続く道筋を作る重要な決断にあたる。

にもかかわらず、本ページは「H / Y / Z / S / T と同じ角丸正方形を継承する」という同族感の強調で議論を閉じており、 multi-character がもたらすトレードオフ (字形バウンディング外形サイズが H の約 1.7 倍、可読 vs 占有のバランス、 paper 部分の占有率が大きく見えてゲートが薄く見える可能性) を明示的に取り上げていない。 字形外形 ≈ 27.3 × 20.1 px は本体 40 × 40 の 約 68 % × 50 %と、H の単文字 (≈ 55 %) と X の Plus (≈ 30 %) の中間ではなく、横方向では H を上回る占有になる。

★ 批評 · Top Opportunities
影響度の大きい改善候補 (各論は本文中の批評ブロックに展開)
  1. multi-character 字形の設計判断を § 04 で明示 — 現状は「√ と X を合成した字形」とだけ書かれ、なぜ "√X" を 1 グリフとして合成するのか (Geist テキスト描画の "√X" 文字列で済まないのか) の根拠が薄い。SDF テクスチャ焼き込みの単位、Quirk 互換性、advance / kerning の問題などを言語化する (§ 04 参照)。
  2. H / X / √X の横並び比較画像を § 01 か § 04 に追加 — 単文字 (H) / Plus (X) / 合成 (√X) の 3 つを 1 枚に並べ、視覚的占有量とゲートとしての「重さ」を 1 目で比較できるようにする。これは sqrt-X が「Pauli 族のはみ出し者」かどうかの判断根拠になる (§ 01 / § 04 参照)。
  3. § 02 配色表の「内側 2 px は下地を見せる」と「内側を surface で抜く」が同じセルに混在 — 回路上とパレット上で異なる実装方針を 1 つの備考欄に詰め込んでおり、読者には文脈が伝わりにくい。行を 2 つに分けるか、別表として外に出す (§ 02 参照)。
  4. § 07 の「(√X)² = X」を ブロッホ球図に紐づける — 行列 1/2 [[1+i, 1−i], [1−i, 1+i]] は記号としては書かれているが、「2 回適用すると |0⟩ → |1⟩ に反転する」という直感的な振る舞いをブロッホ球図 (X 軸 90° → 180° の二段アニメ) で示すと、初学者の理解が深まる (§ 07 参照)。
  5. Quirk 互換の字形表記 ("√X" vs "X1/2" vs "√X") — Quirk は HTML エンティティ &radic;X で表示する。本仕様は SVG path での字形合成だが、論文表記との対応 (X^(1/2) や X^{1/2}) が説明されていない。コード識別子 (GateKind::SqrtX 等) との対応も含めて明文化する。

§ 01概要 (見た目と用途)

√X は X 軸まわりの π/2 回転に相当し、2 回続けて置くと Pauli-X と同じ作用になる。 見た目では「半分の X」を別色や半透明で示さず、cyan-400 = ユニタリ操作ゲートという既存の色対応を守る。 √X 固有情報は字形そのものと説明文に閉じ、X ゲートの円形ターゲット記号とは混同させない。

★ 批評 · § 01 概要
「X の平方根」という意味論と、見た目が X (円) と一致しない設計判断のトレードオフが言語化されていない

本文は「√X 固有情報は字形そのものと説明文に閉じ、X ゲートの円形ターゲット記号とは混同させない」と結論を書くが、 その判断の根拠は読者が § 02 配色や § 07 設計判断まで読まないと拾えない。 √X は X の平方根 (2 回かけると X になる) という強い意味論的つながりを持ちながら、見た目では完全に X と分離している。 この設計の妥当性 (CNOT ターゲットとの混同回避 vs 意味論の視覚化) は本ページの最初の問いであり、§ 01 で明示すべき。

改善案: § 01 の最初の段落で「X = 円形 + Plus、√X = 角丸正方形 + √X 字形」という対比を 横並び画像で先に示し、 その後に「なぜ X と同形にしないか」(円形 = CNOT ターゲット予約、√X は CNOT 半分操作ではないので別形状) を 1 段落で述べる。 現状の構成は意味論 (「X 軸まわりの π/2 回転」) → 色対応 → X との切り分け の順で、設計の核心が最後に来ている。

★ 批評 · § 02 配色 / ホバー枠の二重記述
「回路上は本体外側 4 px の外枠に 2 px 線」と「パレット上は内側を surface で抜く」が 1 セルに混在

ホバー枠の備考列は「回路上は本体外側 4 px の外枠に 2 px 線だけを描き、内側 2 px は下地を見せる。パレット上は内側を surface で抜く」と、 2 つの異なる文脈 (回路 vs パレット) を 1 つの備考に圧縮している。h-gate.html / y-gate.html / z-gate.html の配色表は 「本体外側 4 px、内側に 2 px の背景の空き」と単一記述で済んでおり、本ページだけが二重記述を持つ。

実装の事実として、回路 (canvas) では rect_stroke の線だけが描かれ、内側 2 px の下地は wire や背景が透ける。 一方パレット (HTML) では surface 色で内側を塗り潰す。この差は hover-frame.html primitive に 集約されるべき情報であり、本ページの配色表は「ホバー枠 = purple-400 + 4+2 幾何」と書くだけで、 詳細を hover-frame.html に委ねたほうが読みやすい。

さらに、本ページの CSS は box-shadow: 0 0 0 2px var(--bg), 0 0 0 4px var(--purple-400) で実装している。 これは「内側 2 px を bg で塗る」方式で、回路実装の「内側 2 px は下地を見せる」とは厳密には異なる (下地 = bg であれば視覚は同じ)。本仕様ページが「回路実装」と「パレット実装」のどちらを再現しているかは 本文に書かれておらず、これも読者には判断できない。

★ 批評 · § 04 字形 (√X)
Pauli 族の単文字原則を初めて破る √X 字形の設計判断が「合成」とだけ語られている

H / X / Y / Z の Pauli 族は 1 グリフ = 1 文字 (または 1 記号) という原則で揃っており、本仕様の表でも H は単文字 viewBox 0 0 48 48 内 scale(0.029760)、Y / Z も同じスケールで配置される。 √X は初めてこの原則を破り、2 つの SVG <g> ブロック (√ と X) を別々の transform で合成している。 √ は scale(0.025296)、X は scale(0.029760) と、スケールも一致しない (√ のほうがやや小さく、X は H / Y / Z と同じ単文字スケール)。

この実装方針は妥当だが、本表の「形式」「√ の変換」「X の変換」と分けて並べるだけで、なぜこの方式かの根拠が薄い。 代替案は (a) Geist テキスト描画の "√X" 文字列で描く (font kerning に任せる)、 (b) "√X" を 1 つの合成グリフとして外部ツールで作り、SVG path に焼き込む、(c) 現状の SVG <g> 2 層合成。 (a) は font の √ グリフがゲートチップの中で細く見えがち、(b) はメンテコスト高、(c) は実装/設計コスト中だが、 Geist の √ と X の本来サイズ比をそのまま使えるので採用された、と推測できる。 本表に判断軸を 1 段落加えると、RX / RY / RZ など他の multi-character ゲートを実装するときの参考になる。

補足: 字形外形 ≈ 27.3 × 20.1 px は本体 40 × 40 の横方向 68 %、縦方向 50 %。 単文字 H が 横 24 % × 縦 53 %、X の Plus が 横縦とも 30 %と比べると、横方向の 占有率が突出している。これは "√" の腕が左に伸び、"X" が右に置かれる合成幾何の必然だが、回路上で √X が他のゲートより 「重く」見える可能性は要検証 (Top Opportunities の H / X / √X 横並び比較で検証可能)。

§ 07意味論と設計判断

行列
√X = 1/2 [[1+i, 1−i], [1−i, 1+i]]
基底状態
√X|0⟩ = (1+i)|0⟩/2 + (1−i)|1⟩/2
√X|1⟩ = (1−i)|0⟩/2 + (1+i)|1⟩/2
ブロッホ球
X 軸まわりの π/2 (90°) 回転。Z 軸上の |0⟩ / |1⟩ を ±Y 方向へ移す。
関係
(√X)2 = X。Rx(π/2) と同等の回転を、グローバル位相を除いて表す。
  • H / Y / Z / S / T と同じ角丸正方形にする: √X は文字グリフで識別する通常の 1 量子ビットゲート。X だけは CNOT ターゲットと同じ ⊕ 記号を共有するため円形にする
  • 字形は √ と X の合成ベクタに固定する: ブラウザのテキスト描画に任せると √ の腕と X のベースラインがずれる。apps/web/assets/icons/sqrtx.svg と同じ path を使い、パレット / 回路 / 仕様ページの字形をそろえる
  • 「平方根」を色や半透明で表現しない: 半分の操作であることを色で示すと、ホバー / ドラッグの状態色と衝突する。演算の関係は字形とツールチップ、状態遷移の説明に任せる
  • X ゲートとの関係を明示する: (√X)2 = X がもっとも重要な意味論。見た目は X と同色だが、円形 + Plus にはしないことで CNOT ターゲットとの混同を避ける
  • span = 1 固定: √X は単一量子ビットだけに作用するため、表示ブロックや QFT のような span リサイズを持たない
★ 批評 · § 07 意味論と設計判断
「(√X)² = X」の意味論はカードに書かれているが、ブロッホ球図がない

matrix-card の「ブロッホ球」カードには「X 軸まわりの π/2 (90°) 回転。Z 軸上の |0⟩ / |1⟩ を ±Y 方向へ移す」 と書かれており、これは √X の本質を端的に示している。一方で、2 回適用すると |0⟩ → |1⟩ になる (X 軸 90° + 90° = 180° 回転) という連鎖の図示はない。これは √X が X の平方根であることを視覚化する最短経路で、 「行列を 2 回かけたら X 行列になる」と書くより直感的に伝わる。

bullet 4「X ゲートとの関係を明示する」は重要な判断だが、「見た目は X と同色だが、円形 + Plus にはしない」とだけ述べる現状は、 本ページの最初の問い (なぜ X と同形にしないか) への答えとしては薄い。同色 (cyan-400) を共有しているのに形だけ違うのは、 Pauli 族で唯一 X が 形 (円) で機能を表す例外であり、√X は X の半分操作だが「CNOT のターゲット予約」を 奪うほどの単独存在感はないから、と書くと根拠が明確になる。

bullet 3「平方根を色や半透明で表現しない」は良い判断だが、半透明 (opacity) を捨てた理由を 1 行加えると、後続の S† / T† / SqrtX† など 逆ゲート仕様での「dagger をどう視覚化するか」の議論につながる。 Quirk は逆ゲートを字形に小さな † を加えて表現する方針で、qni-webgpu も同じ路線なら明文化する余地がある。

補足 (字形と意味論の対応): matrix-card 4 つのカードはすばらしいテンプレートで、Y / Z ページにも同じ構造がある。 √X / Y / Z で共通テンプレートを切り出し「unitary-gate-semantics.html」のような親仕様にすれば、X (Plus / 円形) も 同じ意味論カードを使って統一できる (X ページは現在意味論カードを持たない)。
