アンチコントロールゲート (|0⟩ 条件)

AntiControl は同じ列の対象ゲートを |0⟩ 条件にする制御マーカ。 回路エディタ上では 40 × 40 px の透明な領域の中央に、 cyan-400 の 空円 (r=5, stroke=3) を描く。 空円の内側だけは bg-2 の小さな円でワイヤを隠し、マーカの穴に線が入らないようにする。 塗りつぶし円で |1⟩ 条件を示す Control と 本体寸法 / 色 / 当たり判定をすべて共有し、「塗りか線か」だけで条件値の違いを示すペア表現を採用する。

★ 批評 · 全体所見
Control とのペア仕様だが、識別性 (塗り vs 線) の妥当性が「ペア表現を採用する」の一言で済まされている

AntiControl は Control と寸法 / 色 / 当たり判定をすべて共有し、字形 (塗り / 線) だけで条件値の違いを示すペア表現。 この設計判断は page-lede で明示されており、本仕様は Control 仕様の sibling として一貫性が高い。 一方で 「塗り vs 線」だけが唯一の識別軸という前提が、可読性 / アクセシビリティ / 視認性の観点から じゅうぶん検証されていない。実表示 外半径 ~5.4 px (外径 ~10.8 px) / 線幅 ~2.5 px の空円は、画素グリッドにきれいに乗らず、 高 DPI ディスプレイ以外では線の太さが安定しない (アンチエイリアスで滲む)。Control の塗りつぶし円 (外径 ~13 px) との絶対サイズ差も大きく、「ペア」と呼ぶには形状の重心がずれている。

ホバー枠 (purple-400 4 + 2 構成) / Tailwind スケール厳守 / drag preview = purple-600 の議論は H ページの全体所見と同じため再展開しない。本仕様の固有論点は (a)「線だけ」での識別性、(b) コネクタの ±6 px 隙間という空円特有の例外処理、 (c) Control と並んだ時の見分けやすさの 3 つに集中している。

★ 批評 · Top Opportunities
影響度の大きい改善候補 (各論は本文中の批評ブロックに展開)
  1. Control と AntiControl の「直接比較」モックを § 01 or § 03 に追加 — 現状は両者を並べて見せる図がなく、識別性 (空 vs 塗り) の妥当性を Codex / 人間が検証できない (§ 01 参照)。
  2. 外半径 ~5.4 px (外径 ~10.8 px) / 線幅 ~2.5 px が Tailwind スケール外 — viewBox 48 → 40 px 表示の換算結果で、Tailwind の spacing-* や border-* スケールに乗らない非整数。実装側で固定化されているとはいえ、仕様で明示する妥協 (§ 02 / § 03 参照)。
  3. コネクタ ±6 px 隙間の根拠が「空円外半径 ~5.4 px を完全に避ける幅」だけ — なぜ 5 px / 7 px / 8 px ではなく 6 px か、視覚的な検証ロジックが弱い (§ 03 参照)。
  4. § 05 column-mock--anti-middle の SVG / CSS 表現が見た目仕様 (実装) と乖離するリスク — CSS の linear-gradient 2 段重ねで隙間を表現しているが、これは実装 (Rust + WebGPU) の二本線描画と異なる表現手段。仕様ページの再現性として論点 (§ 05 参照)。
  5. 多重制御 (CCCX 等) で Control / AntiControl が混在する場合のコネクタの色 / 太さの安定性 — § 05 mini-card で言及はあるが、視覚図がない (§ 05 参照)。
  6. § 04 hover の box-shadow による枠と Control の ::before による枠が技法的に違う — 同じ「purple-400 stroke-only 2 px」枠なのに、Control 仕様は ::before + border、本仕様は box-shadow。実装と仕様の差なのか、仕様内の表記揺れか (§ 04 参照)。

§ 01概要 (見た目と用途)

AntiControl 自体は状態ベクトルを直接変えない。列内の対象ゲートに「対象ワイヤが |0⟩ のときだけ作用する」条件を付ける修飾子として働く。 たとえば AntiControl と X を同じ列に置くと、対象ビットが 0 のときだけ X を適用する「0 条件 CNOT」になる。 塗りつぶし円の Control と空円の AntiControl は 1 つの列内で混在させても良い。

(zoom ×3)
0 条件 CNOT

空円の中心はワイヤと縦コネクタの両方が通る位置にあるため、視覚を阻害しないよう 横ワイヤは空円内側の bg-2 マスクで消し、縦コネクタは空円の中心から上下 6 px を分割描画する。 Control (塗りつぶし円) ではコネクタが本体を貫通しても潰れないので、隙間は空けない。

★ 批評 · § 01 識別性
「ペア表現」と呼びながら Control の塗りつぶし円が並べられていない

page-lede では 「塗りか線かだけで条件値の違いを示すペア表現」を採用すると明言しているが、 § 01 のモック (既定 / 原寸 3 倍 / 0 条件 CNOT) はすべて AntiControl 単体で、 肝心の Control (塗りつぶし円) と AntiControl (空円) の直接比較が無い。ペアとして読ませたい設計判断と ペアの片方しか見せない図解の間に明らかな乖離がある。

改善案: § 01 のステージ右端に「Control + AntiControl 並列 1 行」モックを追加 (例: 左から Control 1 つ → AntiControl 1 つ → 同じ列の Control + AntiControl + X)。これがあれば、初学者でも「塗り vs 空」の識別軸が一目で理解できる。 外径 / 線幅 / 色がすべて共通であることも自明になり、本仕様が Control 仕様とペアであることが視覚的に伝わる。

補足: 原寸 3 倍 (zoom ×3) は H ゲート § 04 の批評と同じく、現代のディスプレイ + Playwright ワークフローでは 情報価値が低いが、本仕様の場合は 「外半径 ~5.4 px (外径 ~10.8 px) / 線幅 ~2.5 px」という非整数の小さい記号なので、 H ゲートの 22 px グリフよりは zoom の意義が残る。ただし zoom ×3 単体ではなく、Control の zoom ×3 と並列に 並べると識別性のチェックとして機能する。

★ 批評 · § 02 配色テーブル
「空円の内側 = bg-2」が配色行として並ぶが、実体はマスクのための背面色であり「色」ではない

テーブルの 2 行目「空円の内側」は bg-2 となっているが、これは「描く色」ではなく 「ワイヤを消すために重ねる背景マスクの色」で、概念的には他の行と性質が異なる (前景色 vs 背面マスク)。 他のゲート仕様 (Control / Swap) には「マスク色」という軸が存在しないので、本仕様だけ 配色ロールが 1 つ多いことを明示しないと、Codex が「box_fill + bg-2 マスク」というパターンを 他ゲートにも適用してしまう懸念がある。

改善案: テーブルから「空円の内側」行を分離し、「視覚仕様: マスク / コネクタ隙間」のような 小節を独立させる (配色 vs 視覚処理を分ける)。または「ロール」列を追加して foreground (前景色) / mask (背面マスク) / connector / hover / drag を明示する。 現状の表は「配色 = 色面」と読まれやすく、bg-2 マスクの存在が読み飛ばされやすい。

補足: 条件値の 0 / 1 を別色で区別しない判断はじゅうぶん理にかなっているが、これに例外が無いことの根拠は薄い。 たとえば回路エディタの「条件値ハイライト」モード (シミュレーション中、現在の基底に含まれる条件のマーカだけ強調) のような将来機能を考えると、今のうちに「色変化が許可される文脈はあるか」を 1 行明記しておくと、将来のドリフトを防げる。

★ 批評 · § 03 ジオメトリ
コネクタ ±6 px 隙間の根拠が「外半径 ~5.4 px を完全に避ける幅」だけで、上限の設計余裕が無い

現状の根拠は「空円の外半径 ~5.4 px を完全に避ける」のみで、なぜ 6 px なのか (下限) は分かるが、なぜ 7 px / 8 px ではないのか (上限) が示されていない。コネクタ隙間が大きすぎると「2 端点が同一操作である」という視覚的結びつきが弱まる。 たとえば隙間 8 px なら全コネクタ長 56 px のうち 16 px (28 %) が抜けることになり、AntiControl が「列の中間ノード」になる ケースで上下のコネクタ片が「別の操作」のように見えてしまう。6 px は下限ぎりぎりの最小値で、設計余裕は片側 ~0.3 pxに過ぎない。

さらに、空円の外半径 ~5.4 px もviewBox 48 → 40 px 表示の換算 (5 + 1.5 → 6.5 / 48 × 40 ≈ 5.42) で 非整数になる。実装側で SDF / アンチエイリアスがどう描いても画素グリッド上では ±0.5 px の揺れが出るので、 厳密には 6 px の隙間もサブピクセル分のオーバーラップ余地を持つべき。 本仕様は「外半径 ~5.4 px / 隙間 6 px = 余裕 ~0.6 px」と書くと、将来 stroke-width / r を調整する際の根拠になる。

SVG 内 font-size="4" ≒ 実表示 12 px は Tailwind スケール内だが、SVG の Geist Mono はサブピクセルラスタライズが効きにくい。 h-gate.html § 03 / control-gate.html § 03 と同じ論点。同様に、SVG 中の空円が cx="20" cy="20" r="5.4" stroke-width="2.5" と 非整数ベースで描かれているため、SVG プレビューと実 GPU 描画 (SDF / outline) で見た目が微妙に異なるリスクがある。 Playwright スクショによる比較を別途仕様化しておくと安心。

★ 批評 · § 04 状態バリアント
CSS の hover 枠を box-shadow で描いており、Control の ::before + border と技法が違う

本ページの hover は box-shadow: 0 0 0 2px var(--purple-400) で描かれており、 Control 仕様の ::before { inset: -4px; border: 2px solid } と 異なる CSS 技法を使っている。同じ「purple-400 stroke-only 2 px」の見た目を、片や box-shadow、片や擬似要素 + border で 描いており、仕様ページ間の一貫性が崩れている。

box-shadow と border は枠の位置 (本体外側 / 内側) が異なる: box-shadow: 0 0 0 2px は本体外周に密着して 2 px を足すため、 ホバー時に隣接スロットへ 2 px 食い込む。Control 仕様の inset: -4px + border 2px は本体から 4 px 離れて 2 px を描くため、 合計 6 px の hover halo になる。本仕様の hover は Control より枠の位置が違う可能性がある。 実装側 (gate-palette.html / hover-frame.html) と照合し、どちらが正しいかを統一すべき。

補足: 「回路ホバー = stroke-only / パレットホバー = surface gap」の使い分け根拠が caption に出ていない論点は、 Control 仕様 § 04 の批評と同じ。Control / AntiControl / Swap で共通の論点なので、 hover-frame.html 側に横断仕様として記述するのが筋。

§ 05列内の接続と意味論

制御条件は列単位で集計する。AntiControl は 条件マスクには立てるが、条件値は 0 のままにする。 対象ゲートは「同じ列の制御マーカが全て条件を満たした基底成分」にだけ作用する。 塗りつぶし制御と反制御を同じ列に置くと、それぞれが |1⟩ / |0⟩ 条件として AND で組み合わさる。

AntiControl + X
0 条件 CNOT
Control + AntiControl + X
混在多重制御
単独配置
対象ゲートがない単独の反制御マーカは操作なし。視覚上の縦コネクタも出さない。
反制御だけの列
対象ゲートがなく反制御だけが並ぶ列は意味のない操作になるため、回路コンパイル時に無視する。
制御との混在
同じ列に Control と AntiControl を混ぜると、各ビットが対応する条件値のときだけ対象ゲートが作用する多重制御になる。
Swap との関係
Swap の縦線は専用コネクタで描く。反制御付き Swap の条件は同じ列の制御条件を共有する。
★ 批評 · § 05 列内集約
「中央が AntiControl」の CSS 表現が実装と乖離するリスク、CCCX 等の混在ケースの図解も欠落

2 つ目のモック (Control + AntiControl + X 混在) は .column-mock--anti-middle::after の linear-gradient 2 段重ねで「上半分 50 px → 12 px 空き → 下半分 50 px」を表現している。 これは CSS による視覚再現として有効だが、実装側は apps/web/src/render/circuit_connectors/control.rs で 個別の矩形ストロークを 2 つ描くはず。CSS の表現手段と実装の表現手段が違うので、 将来コネクタの隙間や色が変わったとき、本ページ側だけ古い CSS 値が残るリスクがある。

改善案: § 03 の geo-diagram と同じ inline SVG でコネクタ片 2 本を描くと、「viewBox / 矩形の位置とサイズ」という 実装と同じ語彙で描けるため、仕様 / 実装間のドリフトを検出しやすい。 本ページの linear-gradient の 0 0 / 100% 50px no-repeat, 0 62px / 100% 50px no-repeat は マジックナンバーが 2 箇所 (50 と 62) あり、--connector-gap 等の CSS 変数化もできていない。

さらに、3 量子ビット以上の混在ケース (例: Control × 2 + AntiControl × 1 + X = CC̄CX 相当) や、 AntiControl が両端と中間に同時にあるケース (例: AntiControl - X - AntiControl) でコネクタの隙間が 2 つ以上発生するパターンの図解が無い。実 UI で起きうる組み合わせなので、§ 05 で 1 行図示すると Codex が コネクタ実装の境界条件を理解できる。
