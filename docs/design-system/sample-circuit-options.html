QNI WebGPU · Circuit picker / Sample circuits

サンプル回路をユーザ回路と区別し、誤編集から守るための UI 案

Bell / GHZ / QFT-4 / Grover Search のような同梱サンプルを circuit picker に並べると、ユーザが作った回路と見分けがつかず、サンプルを編集して元に戻せなくなる。この文書では 5 つの案 (A〜E) を提案し、トレードオフを比較する。

00

背景

現在の挙動では、起動時にサンプル 4 件が生成され、ユーザが新規作成した回路と同じ保存領域に同居する。両者はドロップダウン上で区別表示されない。サンプルを編集すると内容が上書きされ、元の定義に戻す手段がない。

4

同居

01

解決したい 3 つの摩擦

サンプルをライブラリに同居させる以上、以下の摩擦が常に発生する。案ごとにどれを解消し、どれを残すかを明示する。

P1

区別不能

サンプルかユーザ回路かが視覚的にわからない。「Grover Search」を消していいのか迷う。

P2

破壊的編集

サンプルを開いて少し試した結果が元の定義を上書きする。初期状態に戻す導線がない。

P3

追加・更新の衝突

アプリ更新でサンプルを増やす / 内容を直すとき、ユーザの編集済みインスタンスをどう扱うか方針がない。

案 A · バッジ + 編集前ダイアログ

OPTION A最小導入 · 既存ドロップダウン据え置き

サンプルにだけ「SAMPLE」バッジを付与し、編集が始まる瞬間に「複製して編集しますか？ / そのまま編集しますか？」を確認する。同居・編集許可のまま、視覚と確認だけ追加する案。

利点
  • UI 構造を変えない。

04

案 B · ドロップダウン内 2 セクション

OPTION B中庸案 · セクション見出しで明確に区切る

「サンプル」と「マイ回路」を見出しで分け、サンプルをクリックすると自動的に「マイ回路」へ複製して、複製先をアクティブにする。サンプルそのものは常に原型のまま残る (実質 read-only)。

05

案 C · サンプルをギャラリーに分離

OPTION C大胆案 · ドロップダウンには「マイ回路」だけ

サンプルはピッカーから完全に外し、「+ New」の隣に「+ From example…」エントリを置く。クリックでサンプルギャラリー (sub-popover or modal) を出し、選んだ瞬間にマイ回路へインポートする。ピッカー本体はユーザ回路だけになる。

設計範囲

サンプル一覧を初回起動処理から切り離し、ギャラリー用のサブポップオーバーとして扱う。

06

案 D · Copy on Edit (見えないフォーク)

OPTION D魔法案 · ユーザに意識させずサンプルを守る

サンプルは常に read-only にマークする。ユーザが編集操作 (ゲートを置く / 消す / 量子ビット数変更) を始めた瞬間に、自動的にマイ回路へ複製してアクティブを切り替え、編集はその複製に当てる。元のサンプルは触られない。VS Code が読み取り専用ファイルを開いて編集すると「Copy to writable」を促す挙動に近いが、こちらはサイレントに行う。

07

案 E · Origin タグ + Reset to default

OPTION E寛容案 · 編集は許可、いつでも巻き戻せる

サンプルもユーザと同じく自由に編集できるが、種別タグを持たせ、kebab メニューに「Reset to default」を出す。サンプルの標準定義を常に参照できるようにし、「Reset」で初期値に戻す。アプリ更新でサンプル定義が変わったら、未編集のサンプルだけ自動同期する。

回路に種別とサンプル識別子を持たせ、標準定義の対応表を保持する。kebab に Reset 項目を追加する。

09

推奨と段階導入

単独採用なら 案 B (2 セクション + 自動複製) が UI の素直さと安全性のバランスがよい。長期的には 案 D (Copy on Edit) に拡張する余地がある。

Phase 1 · まず案 B
  • 各回路に「サンプル / ユーザ」の種別を持たせる。
  • サンプル一覧をユーザ回路一覧から分離し、初期状態はサンプル + 空のユーザ回路 1 件で始める。
  • ピッカー表示にセクション見出しを挟む。
  • サンプル行の選択を「複製 → アクティブ化」にする。
  • サンプル行の kebab は Duplicate のみに制限。
Phase 2 · 必要なら案 D
  • サンプル「閲覧」モードを足す: クリック直後はコピーせず read-only で開く。
  • 編集操作の共通入口に「Sample なら fork してから適用」を挿入。
  • fork 直後に toast 表示 (「Forked to My circuits」)。
  • read-only 中はツールバーから保存・URL share を抑止 (or 自動 fork)。
避けたい組み合わせ: 案 A 単独。P3 (更新衝突) の方針がないまま編集を許可するとアプリ更新時にユーザのサンプル定義と新定義の差分処理が破綻する。案 A を採るなら最低でも種別タグ + 案 E の Reset を併用する。
共通の前提: どの案でも回路に「サンプル / ユーザ」の種別を持たせる価値がある。これがあるだけで「サンプル削除を許可するか」「アプリ更新時にどう統合するか」を後から自由に決められる。
次の一歩: Phase 1 (案 B) のうち、まず回路種別とサンプル一覧の分離を独立作業にする。UI のセクション見出し追加は別作業で、スナップショットテストで見た目の差分を確認する。Phase 2 への移行余地を残すため、サンプル選択時の挙動 (「即複製」か「read-only で開く」か) は 1 か所で切り替えられるようにしておく。
