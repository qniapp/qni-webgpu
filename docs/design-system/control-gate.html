制御ゲート (|1⟩ 条件)

Control は、同じ列の対象ゲートを |1⟩ 条件にする制御マーカ。 回路上では 40 × 40 px の透明な領域の中央に cyan-400 の塗りつぶし円を描く。 対象ゲートと同じ列に並ぶと、中心同士を 4 px 幅の縦コネクタで結び、 CNOT / CZ / 多重制御ゲートのような多量子ビット操作として読む。

★ 批評 · 全体所見
「単独マーカ仕様」と「列内集約仕様」の責任境界が曖昧

Control は本体に塗りを持たない「修飾子」ゲートで、本仕様ページは 40 × 40 px の単独マーカと 列内に他のゲートと並んで初めて意味を持つ多量子ビット操作の両方を扱っている。 § 01 / § 04 が前者 (マーカ単体)、§ 05 が後者 (列内集約) を担当する構造は概ね合理的だが、 § 03 ジオメトリで言及される「縦コネクタ 4 px」「z-index = コネクタ→マーカ」はマーカ単体の話ではなく 列内集約レイヤの話で、章をまたいで論理が混在している。

理想的には、「マーカ仕様」と「コネクタ + 列集約仕様」を別ドキュメント (例: circuit-connectors.html) に切り出し、本ページは Control 固有 = 塗りつぶし円 cy=24/r=8 だけに集中するほうが、 AntiControl / Swap と縦コネクタ仕様を共有でき diff レビューの負荷も減る。 実装側の apps/web/src/render/circuit_connectors.rs が CONNECTOR_STROKE_WIDTH = 4.0 を Control / Swap / 同角 Phase で共有していることを§ 06 で言及している以上、仕様側でも共有層を切り出す価値がある。 ホバー枠 (purple-400 4 + 2 構成) / Tailwind スケール厳守 / drag preview = purple-600 の議論は H ページの全体所見と同じため再展開しない。

★ 批評 · Top Opportunities
影響度の大きい改善候補 (各論は本文中の批評ブロックに展開)
  1. 縦コネクタ仕様を circuit-connectors.html に抽出 — Control / AntiControl / Swap が同じ 4 px 仕様を 3 ページで重複定義している (全体所見参照)。
  2. § 02 配色テーブルに「制御マーカ」「縦コネクタ」を独立行で並べる冗長 — 両者は同じ cyan-400 / box_fill ロールで備考だけが違う。「ロール / 適用箇所 / 状態」を分けると共有関係が読める (§ 02 参照)。
  3. § 03 SVG 寸法注記 font-size="4" が Tailwind スケール外 — viewBox 80 を 240 px に投影しているので実表示 12 px だが、SVG mono は判読しにくい。h-gate と同じ論点だが本ページにも該当 (§ 03 参照)。
  4. § 05 列内集約の「単独配置」「制御だけの列」の semantics が文章のみ — どの組み合わせが GPU op に展開され、どれが no-op か、表で並べたほうが Codex / 人間が一覧できる (§ 05 参照)。
  5. 多重制御 (CCX = Toffoli) / 中間ワイヤを跨ぐ場合の縦コネクタ仕様が無い — 「制御 — 制御 — 対象」を 3 行に置いた場合、中間ワイヤ上で何が描かれるかが本仕様に書かれていない (§ 05 参照)。

§ 01概要 (見た目と用途)

制御ゲート自体は状態ベクトルを直接変えない。列内の対象ゲートに |1⟩ 条件を付ける 「修飾子」として働く。たとえば Control と X を同じ列に置くと CNOT、 Control と Z を同じ列に置くと CZ になる。

単体マーカ
|1⟩ 条件
CNOT
制御 + X
ホバー
stroke-only の紫枠

縦コネクタは「この列に制御条件がある」ことを示す補助線。対象ゲートの本体を塗り替えず、 同じ列にある制御マーカと対象の中心だけを接続する。

★ 批評 · § 01 識別性
塗りつぶし円 cyan-400 が単独で何を意味するか、初見では伝わりにくい

Quirk / 量子回路の慣習を知っている読者には 塗りつぶし円 = control = |1⟩ 条件は自明だが、 本仕様だけ読む初学者には「色面のない 6.67 px の塗りつぶし円」は circuit junction (回路の合流点) や wire の中継点とも区別がつきにくい。Hadamard / Pauli のようなグリフを持つゲートは 本体色 + 文字で「何のゲートか」が即読みできるのに対し、Control は「形 = 意味」が完全に Quirk 慣習依存になる。 この前提を § 00 (前文 / page-lede) で明示しておくと、Codex が「なぜ円なのか」の判断軸を理解できる。

さらに、本 § ではモック横並びで「単体マーカ / CNOT / ホバー」を見せているが、 「単体マーカ = 操作なし (§ 05 参照)」という重要な意味論が caption に出ていない。 Control は対象ゲートと組み合わさって初めて意味を持つので、単体モックの caption は 「単体マーカ (操作なし、対象が必要)」のようにセマンティクスも併記する価値がある。

★ 批評 · § 02 配色テーブル
「制御マーカ」と「縦コネクタ」が独立行で並ぶが、両者は同じ box_fill ロールで備考だけが違う

現状のテーブルは 5 行構成だが、上 2 行 (制御マーカ / 縦コネクタ) はどちらも cyan-400 = box_fill ロールで、適用箇所だけが違う。これは 「同じ Flexoki トーンが同じロールで複数箇所に適用される」パターンで、テーブルとしては ロール → 適用箇所のツリーに展開するほうが、配色ロール (token) と描画要素 (instance) の関係が読める。

改善案: テーブルを「ロール / Flexoki トーン / hex / 適用箇所 / 状態」の 5 列に再構成すると、 box_fill (cyan-400) 行に「制御マーカ + 縦コネクタ」と複数適用箇所をまとめられる。 これは AntiControl 仕様 § 02 や Swap 仕様 § 02 と 同じ構造になり、Multi-qubit 家系での一貫性も上がる。

★ 批評 · § 03 ジオメトリ図
SVG 内の font-size="4" は実表示 12 px だが本仕様の他章 (text-xs = 12 px) と書体が違う

geo-diagram SVG は viewBox="-12 -12 80 80" を 240 × 240 px に投影しているので、 font-size="4" の寸法注記 (「56 px slot」「40 px hit area」) は実表示約 12 pxに相当する。 Tailwind スケール (text-xs = 12 px) には乗っているが、SVG 内の Geist Mono はサブピクセルラスタライズが劣化するうえ、 右の .legend ブロックがすでに同じ情報を text-xs (12 px) で並べているため、SVG 内テキストは情報的に重複している。 h-gate.html § 03 と同根の論点 (h-gate は font-size="3.6" = 約 10.8 px とより小さく深刻)。

さらに、SVG 中の円は cx="20" cy="20" r="6.67" と 40 px 実寸換算で描かれているが、 近接する viewBox 内の dashed rect (-8〜48 / 0〜40) は 1 px = 1 SVG unit として描かれ、 スロット内の 同じ図に 2 つのスケール軸が混在している (円: r=6.67 が viewBox 48 → 40px 表示の換算値、 矩形: 40 = 40 px 実寸)。「40 px hit area」のラベルと r=6.67 の円が同居しても、円が viewBox 上の r=8 を表示換算した値 だと初見では分かりにくい。SVG 凡例にこの混在を 1 行明示するか、両方とも viewBox 48 スケールで揃えると整理できる。

★ 批評 · § 04 状態バリアント
「回路ホバー = stroke-only」「パレットホバー = surface gap」の使い分けの根拠が caption に出ていない

② と ④ は本仕様で唯一見た目が二分岐する設計判断 (回路上ではコネクタが透けるので内部をマスクしない、 パレット上はコネクタが無いので surface gap を入れる) だが、caption は「stroke-only」「surface gap あり」と 実装語彙で書かれているだけで、「なぜそうするか」は読者が § 03 / § 05 を読み解く必要がある。 H ゲートの hover は 4 px 枠 + 2 px 背景の空きの 1 種類だけなので、 本仕様で初めて「ホバー枠は文脈で 2 種類」が登場することになる。caption に 「(コネクタが透けるため内部を塗らない)」「(パレットには対象がないため通常版)」のような根拠を 1 行添えるか、 § 末尾の note に集約すると、初見の Codex / 人間が判断軸を取り違えない。

補足: hover-frame.html 仕様側で「Control / Swap / AntiControl は回路上のみ stroke-only」 という横断ルールを明示すれば、本ページの caption は実装語彙のままで済む。現状は仕様の所在が分散している。

§ 05列内の接続と意味論

制御条件は列単位で集計する。Control は control_mask と control_value の両方へ制御ビットを立てる。 対象ゲートは、その制御ビットが 1 の基底成分にだけ作用する。

Control + X
CNOT
単独配置
対象ゲートがない単独の制御マーカは操作なし。視覚上の縦コネクタも出さない。
複数制御
同じ列に複数の制御マーカを置くと、対象ゲートは多重制御になる。
制御だけの列
塗りつぶし制御が 2 個以上で対象がない列は、CZ / CCZ 系として扱う。
Swap との関係
Swap の縦線は専用コネクタで描く。制御付き Swap の条件は同じ列の制御条件を使う。
★ 批評 · § 05 列内集約
「制御だけの列」と「複数制御」の境界条件が曖昧、CCX / Toffoli の図解も欠落

4 つの mini-card は重要な意味論を網羅しているが、「制御だけの列」は 塗りつぶし制御が 2 個以上で対象がない列は CZ / CCZ 系として扱うと書かれている一方、 「複数制御」では同じ列に複数の制御マーカを置くと多重制御になると書かれており、 「対象がない CZ」と「対象がある多重制御」の境界が読者の頭の中で組み立てなければ繋がらない。 さらに CCX (Toffoli) のような 2 制御 + 1 対象は単独カードがなく、「複数制御」の文中で 多重制御 と まとめられているだけ。Multi-qubit 家系で最も登場頻度の高いゲートの一つなので、図入りの単独カードがあると有用。

改善案: 縦軸に「制御の数 (1 / 2 / 3+)」、横軸に「対象ゲートの有無 (なし / X / Z / その他)」を取る 2 次元の組み合わせ表を入れると、CNOT / CZ / CCX / CCZ / CCCX の位置関係と GPU op への展開が一覧できる。「制御だけの列」が CZ 系として扱われる条件 (= 対象ゲートが Z 相当の対角行列のとき集約可) も ここに整理できる。「Swap との関係」は単独カードよりも§ 07 関連仕様の Swap ゲート リンクに集約したほうが本章の凝集度が上がる。

補足: 中間ワイヤ上の縦コネクタ通過の仕様が本章にも§ 03 にも書かれていない。 制御を q0、対象を q3 に置いた場合、q1 / q2 の中間ワイヤ上を 4 px 縦コネクタが通過するが、 その時に 中間ワイヤに置かれた別の 1 量子ビットゲート (例: H) と縦コネクタの z-index 関係や、 中間ワイヤとコネクタが交差する箇所の描画 (コネクタが上、ワイヤが背面 / どちらが上か) が未定義。 実 UI で描画される最頻パターンなので、本仕様 (§ 03 z-index か § 05) で言及する価値がある。
