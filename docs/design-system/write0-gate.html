|0⟩ オペレーション (Reset to |0⟩)

対象量子ビットを 状態 |0⟩ に強制的に再初期化する非ユニタリ操作。 H / X / Rz のような操作ゲートとは違い、cyan-400 角丸正方形の本体を持たず、 透明な 40 × 40 の hit 領域に tx-2 のケット括弧 |⟩ と中央の red-600 のディジット "0" だけを描く。同色対の |1⟩ オペレーション と陣形を共有する。

★ 批評 · 全体所見
「ゲート」と呼びながら唯一非ユニタリな operation の特異性が、仕様ページの構造から伝わりにくい

本仕様は H ページの全体所見と同じく Flexoki に厳密で、寸法 / 配色 / 字形が根拠付きで網羅されている。 cyan-400 角丸正方形を持たないことや、ホバー枠を内側 bg ギャップなしの単線にする判断は、 |1⟩ / 測定 / Spacer / 制御 と共通の「透明マーカ系」クロムとして整理されている点もよい。

一方で、本ゲートは qni-webgpu のゲート群で唯一 (|1⟩ と並んで)「ユニタリでない単独操作」という大きな特異性を持つ。 § 01 と § 07 で operation や非ユニタリと明言してはいるが、§ 03 ジオメトリ / § 04 字形 / § 06 配置までは H / Rz と同じ「ゲート」template を素直に流用しており、「状態を壊して書き込む」という意味論の重さが視覚的に表れていない。 仕様ページの構造として「§ 00 前文 — このページはユニタリゲートと異なる operation を扱う」を明示するか、 非ユニタリ専用の template (例: state-prep-operations.html を親に持つ) を別系統で持つほうが、 X / Reset / Measurement と並んだときの誤読が減る。

§ 01概要 (見た目と用途)

|0⟩ オペレーションは、入力状態に関わらず対象量子ビットを |0⟩ に置き換える 状態準備 (state preparation) ゲート。 ユニタリ変換ではないため、厳密には「ゲート」ではなく operation に分類する。 コード上の識別子は Write0、シリアライズ ID は Quirk 互換の "|0>"。 H / X / Y / Z / Rz など状態を回転させる cyan-400 ゲートと混同しないよう、 本体 fill を持たない透明マーカ + ケット記号で「読み書き系」であることを示す。 色配分は tx-2 = クロム (括弧)、red-600 = データインク (ディジット) の 2 段だけで、 意味は「|0⟩ の 0 = off ビット」を semantic_off ロールにマップして伝える。

★ 批評 · § 01 概要
「ゲート」「オペレーション」「operation」の呼び分けが揺れている

page-title は「|0⟩ オペレーション」、breadcrumb の親は「量子ゲート」、本文中では 「状態準備 (state preparation) ゲート」「operation」「|0⟩ オペレーション」が同じ段落内で混在する。 さらに § 06 では「非ユニタリ操作」、§ 07 では「ゲート」「オペレーション」の両方が出る。 これは「Quirk 互換 ID は "|0>" でゲート扱い、qni 用語では operation」という二重性に由来するが、 読者にとっては「本仕様は何を 非ユニタリゲートと呼ぶのか」が一読では掴みにくい。

改善案: § 01 冒頭で「本仕様では UI 上の表記を「|0⟩ オペレーション」、コード識別子を Write0、回路意味論の分類を「非ユニタリ operation」に固定する」と 宣言する 1 文を入れる。これがあれば、以降の本文 / 関連仕様 / breadcrumb との照合が一発でできる。 現状の「ゲート」呼称は H / Rz の template から流用された残り香に見え、|1⟩ / 測定 と並べたときの 分類軸の根拠が弱い。

★ 批評 · § 02 配色
red-600 を semantic_off に使うが、UI 一般の「red = エラー / 危険」と衝突しないか

本仕様は red-600 = 0 / off、blue-600 = 1 / on を qni-webgpu の UI 全体で固定する方針で、 確率表示 / 測定 / Write0 で一貫させる根拠は強い。しかし red は世間一般の UI で エラー / 警告 / 破壊操作を示す色として強く期待されている (Material / iOS / Bootstrap いずれも destructive = red)。「|0⟩ にリセットする」はユーザにとって 状態を破壊する操作なので、 red が「リセット = 危険」と誤読される余地が残る (実際の意味は「これは 0 ですよ」というラベル)。

現状はメリット (color pair の一貫性) だけが書かれているが、デメリット (「破壊的操作の red」との衝突可能性) は 本ページ単独で意識される必要がある。「Quirk 由来の配色を維持するために UI 一般の慣習を意図的に踏み越える」 と書いておくと、将来「リセット系操作の色を変えよう」という議論が出たときの判断軸になる。

補足: テーブルの「用途」列に 本体 fill (transparent) と ドラッグ時の色変化 (—) という 「色を持たない」行が 2 つあり、これは h-gate.html § 02 の批評で指摘された 「ロール / 状態の軸圧縮」と同じ問題を別角度で抱えている。「色のないものを色テーブルに書く」設計は、 透明マーカ系のゲート全体で見直す価値がある (空欄行に意味があるなら、その意味を列で表現する)。

★ 批評 · § 03 ジオメトリ

テーブル中で「stroke 2 px (= 表示時 1.67 px)」「viewBox 48 上で (6, 5) → (6, 43)」のように viewBox 系の値と実表示 px の値を併記している箇所と、座標系を明示せずに数値だけ書いている箇所 (「ディジット "0" 配置 translate(15.648 33.883)」) が混在している。 スケール係数 (40 / 48 ≈ 0.833) を読者が暗算する必要があり、§ 04 の「外形サイズ viewBox 上で 13.9 × 20.7 → 実 11.6 × 17.2 px」も 同じ二重化を抱えている。

改善案: 表のラベルを 「viewBox 48 系の値」「実表示 (40 px) 換算」の 2 列に明示分離するか、 該当する数値の単位接尾辞を px@48 / px@40 のように記号化する。 現状は「読者が SVG 内部実装を理解している前提」で書かれており、デザイン仕様としては前提が重い。 加えて SVG 内の font-size="4" 寸法ラベル (実表示 ≈ 12 px) は legend ブロックと内容重複しており、 h-gate.html § 03 の批評と同じく「SVG 内テキストを legend に統合」が応用できる。

★ 批評 · § 04 字形
|0⟩ と |1⟩ で字形仕様が二重に展開され、Geist Mono の "0" を選んだ根拠が薄い

本ページの § 04 は "ケット括弧 + ディジット 0" の字形仕様を全て展開しているが、 括弧部分の path / transform / 色は |1⟩ オペレーションと完全に同一で、差分はディジット 1 文字だけ。 2 ページに同じ字形仕様 (stroke 座標、viewBox、scale 係数) を重複展開するのは h-gate.html § 02 全体所見と 同じ "重複展開" の問題で、ket-operations.html (仮) を親仕様として抽出し、各ページはディジット差分だけに集中するほうが 変更時のコストが下がる。

加えて、"0" を Geist Mono のベクタで描く判断についての根拠が薄い。本文には「フォントレンダラに依存しないため」 「slashed zero 防止のためベクタで保持」と書かれているが、Geist (Mono でない通常版) で書かれた他のゲートグリフ (H / X / Y / Z 等は Geist 700) と並んだ時のタイポグラフィ統一性についての説明はない。実装側で Geist と Geist Mono を併用するなら、 その理由 (「数字は Mono のほうが幾何的に均整がとれる」など) を明文化しておくとよい。

§ 05状態バリアント (常時表示モック)

既定に加え、ホバー / ドラッグ状態を data-state 属性で強制したモック。 |0⟩ オペレーションは本体 fill を持たないため、ドラッグ時も括弧とディジットの色は変えない。 ドラッグ状態の識別は cursor (grabbing) と、回路セル外でドラッグカーソル下に出る ホバー枠だけが担う点が、cyan-400 系のゲート (H / Rz など) との大きな違い。

★ 批評 · § 05 状態バリアント
ドラッグ状態が「② ホバー + cursor」と区別不能で、UI 的フィードバックが弱い

本仕様では cyan-400 系ゲートが cyan-400 → purple-600 の本体色入れ替えで「仮配置中」を強く伝えるのに対し、 |0⟩ オペレーションは本体 fill が無いため、ドラッグ中の視覚フィードバックが cursor 変化 + ホバー枠だけになる。 本文も認めているように、これは「うっすらしか目立たない」状態で、ユーザは「ちゃんと掴めたのか?」が cyan-400 系ゲートに比べて分かりにくい。

改善案: ドラッグ中の |0⟩ では ケット括弧の色を tx-2 → purple-600 に置き換える (ディジット "0" の red-600 は維持し、クロム部分だけ "ドラッグ中色" に変える) などの代替案を検討する価値がある。 現状は「色を変えない代わりに、配置先候補スロットのハイライトで位置を伝える」と書かれているが、 その候補スロットハイライト仕様が本ページからリンクされていないため、読者が「ドラッグの見た目はどこで完結するのか」を追えない。

§ 06回路グリッド上の配置

|0⟩ オペレーションは 1 本の量子ビットワイヤ上の単一スロットに置く。スロットは 56 × 56 px 等間隔、 hit 領域 40 px は中央配置で上下左右に 8 px の余白を持つ。 回路頭 (列 = 0) に置けば初期化、途中に置けば部分リセットを表す。 非ユニタリ操作なので、コンパイル時には measurement + 条件付き X を組み合わせた 動的回路にしか写像されない (純粋にユニタリな回路シミュレータでは別経路で実装される) ことに注意。

うっすら入っているスロット境界の ui 線は説明用で、実 UI には描画されない。 隣接スロットへ連続配置しても、hit 領域同士には 16 px の余白が残り、ホバー枠同士が重ならない。

★ 批評 · § 06 回路グリッド配置
UI 描画仕様の章に「コンパイル時の measurement + 条件付き X 分解」が混入している

本章は「§ 06 回路グリッド上の配置」というデザイン仕様の章だが、本文最後で 「非ユニタリ操作なので、コンパイル時には measurement + 条件付き X を組み合わせた動的回路にしか写像されない」と 実行時の回路分解について踏み込んでいる。これは § 07 「意味論と設計判断」の "ユニタリ性" カードに既に書かれており重複している上、 本来「グリッド上の配置 = 寸法 / 余白 / 隣接ゲートとの関係」という UI レイヤと、 「コンパイラ / シミュレータでどう実行されるか」という意味論レイヤを混ぜている。

改善案: § 06 からは「コンパイル時には...」の段落を削除し、§ 07 だけにまとめる。 または、§ 06 が 「配置の意味」 (回路頭 = 初期化, 途中 = 部分リセット) を伝える役割を担うなら、 その部分は残して「動的回路への分解」だけを § 07 へ移す。デザイン仕様の章境界が曖昧だと、 本仕様を見て実装する Codex が「UI のサイズ仕様」と「実行時の回路要件」のどちらを優先するかで迷う。

§ 07意味論と設計判断

対関係
|1⟩ オペレーション と完全な対。 ディジットと色だけが red-600 → blue-600 に入れ替わる。
  • cyan-400 角丸正方形を使わない: H / X / Y / Z / Rz と同じクロムを流用すると「ユニタリ回転」と誤解される。状態を回す操作ではなく「強制的に書き込む」操作なので、ケット括弧 + ディジットという「状態ラベルそのもの」を見せる字形を採用する
  • ケット括弧を tx-2 にする: 括弧自体は意味を持たないただのクロム (区切り記号)。tx-2 で目立たせず、データインクであるディジットを際立たせる。X ゲートの "+" や Rz の文字グリフが paper = #FFFCF0 で本体上にコントラスト 3.4 で乗るのと違い、|0⟩ は背景 (paper) に乗るので、stroke 色は paper にできず、可読な中性トーン tx-2 を選ぶ
  • ディジット "0" を red-600 にする: 色対 red-600 = 0 / off と blue-600 = 1 / on を UI 全体 (確率表示 / Measurement / |0⟩/|1⟩ operation) で 1 つに固定する。緑 / 青 / 紫など他の色を試すと、「on/off の対」という意味が崩れる
  • ホバー枠を内側 bg ギャップなしの単線にする: cyan-400 ゲートでは「本体 + paper 2 px + purple 2 px」の 2 重 box-shadow を使うが、本体が透明な |0⟩ では内側ギャップを取ると ket 括弧と枠の間に余計な隙間が生まれ、可読性が落ちる。純粋な外側 purple-400 単線にする
  • ドラッグ時に色を変えない: cyan-400 ゲートは本体 fill を cyan-400 → purple-600 に差し替えてドラッグを示すが、本体 fill のない |0⟩ ではこの方法が使えない。代わりに cursor: grabbing + 既定のホバー枠で識別する。色を変えない代わりに、drag preview がうっすらしか目立たないため、配置先候補スロットのハイライト (回路グリッド側で別途定義) で位置を伝える
  • パラメタを持たない: Rz / P のような連続パラメタが無く、配置即確定。|0⟩ ↔ |1⟩ の切替は別ゲート (|1⟩ オペレーション) として独立に並べる方が、palette / 回路上での識別が早い
  • span = 1 固定: 多量子ビット同時リセットは複数 |0⟩ オペレーションを縦に並べて表現する。表示ブロックや QFT のような span リサイズは持たない
★ 批評 · § 07 意味論と設計判断
「X ゲートと分けて持つ」根拠が semantics 中心で、UX (即座の判別性) が薄い

本章の matrix-card で「Kraus 表現」「ブロッホ球北極への強制移動」と semantics が丁寧に書かれている一方、 初学者の UX 観点 — つまり「画面で X と |0⟩ オペレーションがどう違って見えるか」「どちらが ユニタリ / 非ユニタリかを一目で判別できるか」が薄い。 X ゲートは cyan-400 角丸正方形 + paper グリフ "X"、|0⟩ は 透明 + tx-2 括弧 + red-600 "0"で、 クロム自体は確かに別物だが、Quirk ユーザは「X = bit flip」「|0⟩ = リセット」を経験で覚えているだけで、 本仕様だけ読んで 非ユニタリだから分けたと理解できる読者は少ない。

改善案: § 07 末尾に 「X ゲートと |0⟩/|1⟩ オペレーションの並列比較ダイアグラム」を追加する (1 つのスロット内に X と |0⟩ を並べ、「左 = ユニタリ / 右 = 非ユニタリ」をクロムの違いと一緒に見せる)。 h-gate.html § 02 全体所見が指摘した「ユニタリゲート族の親仕様」と相補的に、 「非ユニタリ operation 族の親仕様」(write0 / write1 / measurement) を持つほうがよい議論にもつながる。

補足: 7 項目が平等に並んでいる構造は h-gate.html § 07 と同じ問題を抱えており、 (a) 透明マーカ系で共通 (cyan-400 を使わない / ホバー枠単線 / ドラッグ色変えない) と (b) Write0 単独 (ディジット "0" = red-600 / 北極へ強制移動) を階層化したほうが、 将来 Write1 / Measurement を編集するときに「どこが共通で、どこが個別か」が分かる。
