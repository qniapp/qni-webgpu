Lock / Unlock ボタン

回路ピッカーを Example Circuits と My Circuits の 2 セクションに分ける際に必要な 「現在の回路が編集可能か」を示すトグルボタン。複製アイコンの直右に追加し、 Lucide lock / lock-open を outline で 24×24 → 18 px に描画する。 既存トップバー (apps/egui-web/src/render/toolbar.rs) の規格と完全に揃える。

方針 (案 B の改訂): sample-circuit-options.html 案 B の「Example 選択時に自動で My Circuits へ複製してアクティブ化」は、 サイレントなフォークでユーザが知らぬ間に別物を編集している混乱を生むため採用しない。 本仕様では Example は直接アクティブ化し、トップバーの lock ボタンを tx-3 disabled で固定表示することで「これは編集できない、Duplicate して編集」を明示的に伝える。 Duplicate を明示的に押した時だけ My Circuits にコピーが作られる。

§ 01 動くモック

実物相当のトップバーと回路ピッカー。回路名をクリックすると Example Circuits / My Circuits のドロップダウンが開く。 Example を選ぶと lock は固定 (tx-3 disabled)、 My を選ぶと lock がトグル可能 (unlocked: 透明背景 / locked: ui 背景ピル)。 ロックボタンにマウスを乗せるとツールチップが状態に応じて切り替わる。

§ 04 編集禁止の不変条件

locked = 「その entry の中身を書き換える mutation を一切受け付けない」。 Example Circuits は常時 locked、My Circuits はユーザが lock ボタンで明示的に切り替え可能。 locked は entry の circuit_json と name の両方を凍結する (ゲート編集 / ゲート配置 / Clear / Undo/Redo / 実行中の URL hash 適用 / Rename / Delete を抑止)。 一方、circuit_json / name を書き換えない操作、または unlock のためのメタ情報更新は locked でも通す: Select (active 切替) / Duplicate / Create new circuit / My 内 reorder (順序は別管理) / locked My の lock toggle (origin.User.locked のメタ情報更新で unlock 経路)。

Create new circuit は active が何であっても常に許可する (origin: User { locked: false } の新 entry を末尾に追加して active 化、上書き mutation ではない)。 Lock toggle は localStorage に永続化するが undo history には積まない (履歴は circuit の編集を扱う単位で、メタ状態は別)。

実装ガード: ガード対象は active 編集系と picker 行操作で対象 entry が異なる。

  • active 編集系 (active entry の circuit_json を書き換える): place_gate / remove_gate / clear_circuit / undo_circuit / redo_circuit / apply_url_payload → 入口で self.library.active_locked() を確認、true なら早期 return。 副作用としてトップバー側の Undo / Redo / Trash ボタンも disabled 表示。
  • picker 行操作 (任意 entry の name / 存在を変える): rename(entry_id, new_name) / delete(entry_id) → 入口で self.library.entry_locked_by_id(entry_id) (= origin が Sample または User { locked: true }) を確認、true なら早期 return。 active が unlocked My でも、対象行が locked My / Sample なら拒否されるのが正しい挙動。 submenu 表示時の disabled 判定とは別に、commit / delete の API 側でも必ず再チェックする (UI 競合や直接呼び出し対策)。

ガード対象外 (locked でも通す): toggle_circuit_lock (メタ情報 origin.User.locked のみ更新。 active が Sample の場合は API 側で no-op: Sample variant に locked フィールドが無いのでトグル対象が存在しない) / move_up / move_down / reorder (順序は別管理、entry の中身は触らない) / duplicate / select / create_new (新 entry または active 切替で escape hatch)。

CircuitEntry スキーマ拡張

現行の CircuitEntry は id / name / circuit_json / updated_at のみ。 lock 仕様には origin (Sample 由来か User か) と User の場合の locked 状態が必要。 Sample variant は locked フィールドを持たないことで 「Sample + 非 locked」という不正状態を型レベルで表現不能にする。 

// apps/egui-web/crates/circuit-library-model/src/lib.rs
#[derive(Clone, Debug, Serialize, Deserialize, PartialEq, Eq)]
#[serde(deny_unknown_fields)]
pub struct CircuitEntry {
    pub id: CircuitId,
    pub name: String,
    pub circuit_json: String,
    pub updated_at: u64,
    pub origin: CircuitOrigin,   // 新規
}

#[derive(Clone, Debug, Serialize, Deserialize, PartialEq, Eq)]
#[serde(tag = "kind", rename_all = "snake_case", deny_unknown_fields)]
pub enum CircuitOrigin {
    Sample { origin_id: String },   // 常時 locked (locked フィールド無し)
    User   { locked: bool },         // ユーザがトグルで切り替え
}

tag = "kind" + rename_all = "snake_case" で JSON 上は {"kind":"sample", "origin_id":"bell"} / {"kind":"user", "locked":true} の internally-tagged 形式。 deny_unknown_fields で未知フィールドを silently 受理しない(例: 破損データで Sample variant に locked が混入していたら deserialize エラー)。 これで「Sample + locked」が保存形式レベルでも表現不能 = 起動時に detect 可能。

付随する書き換え: CircuitEntry のフィールドが増えるので、シリアライズ経路を網羅的に更新する。

  • circuit_library.rs の localStorage read/write (JSON serde で origin も入出力)。
  • CircuitLibrary::to_test_json() も origin / locked をエクスポート (snapshot test の比較対象に含める)。
  • test_hooks.rs 経由で JS から見るデバッグ JSON も origin を含める (Playwright 側で `entry.origin.kind === "sample"` などで判定可能に)。
  • seed の hard-coded const に origin: CircuitOrigin::Sample { origin_id: id.to_owned() } を付与。

派生 helper: 

impl CircuitLibrary {
    pub fn active_kind(&self) -> CircuitKind {
        match &self.active().origin {
            CircuitOrigin::Sample { .. } => CircuitKind::Example,
            CircuitOrigin::User { .. }   => CircuitKind::My,
        }
    }
    /// Sample なら常に true。壊れた保存データで Sample + 非 locked になることはない。
    pub fn active_locked(&self) -> bool {
        match &self.active().origin {
            CircuitOrigin::Sample { .. } => true,
            CircuitOrigin::User { locked } => *locked,
        }
    }
}

pub enum CircuitKind { Example, My }

localStorage 移行 (v1 → v2)

v1 では seed sample もユーザが編集できたので、id だけで「Sample 確定」と判定するのは危険 (編集済みのユーザ回路を読み取り専用に閉じ込めてしまう)。 v2 では「公式 sample は const から再生成」「v1 entry が公式 sample の id を持っていても、 内容 (canonical JSON + name) が一致しなければ User コピーへ退避」を行う。

保存形式 (v2 document JSON)

{
  "version": 2,
  "active_id": "ckt_20260518_my-experiment",
  "entries": [
    {
      "id": "bell",
      "name": "Bell state",
      "circuit_json": "{\"cols\":[[\"H\"],[\"•\",\"X\"]]}",
      "updated_at": 1778727600000,
      "origin": { "kind": "sample", "origin_id": "bell" }
    },
    {
      "id": "ckt_20260518_my-experiment",
      "name": "my-experiment",
      "circuit_json": "{...}",
      "updated_at": 1778740000000,
      "origin": { "kind": "user", "locked": true }
    }
  ]
}

origin は { kind: "sample", origin_id } | { kind: "user", locked } の internally-tagged 形式 (Rust #[serde(tag = "kind", rename_all = "snake_case")])。 Sample variant に locked フィールドを持たせないことで、保存形式レベルでも「Sample + 非 locked」が表現不能。

移行手順 (migrate_v1_to_v2())

  1. キーは qni.circuit_library.v2 に bump。古い qni.circuit_library.v1 はv2 validate 成功まで残す(復旧余地)。
    • 初回起動: v2 が無い → v1 を読んで migration → v2 を書き込んで validate (parse round-trip + schema 確認)。validate 成功するまで v1 は削除しない。
    • 2 回目以降: v2 を読む。v2 read / validate に失敗かつ v1 が残っていれば、v2 を退避 (qni.circuit_library.v2.broken-{ts}) してv1 から再 migration + v2 書き直し。tracing で警告。
    • v2 validate 成功した次回起動で初めて localStorage.removeItem("qni.circuit_library.v1") を実行。
  2. v2 seed: CircuitLibrary::seed() が hard-coded const から Sample entries (bell / ghz / qft-4 / grover-search) を生成、常に含める。
  3. v1 entries を 1 件ずつ処理:
    • id が seed sample ID と一致し、circuit_json と name が canonical 定義と完全一致 → 廃棄 (v2 seed と重複)
    • id が seed sample ID と一致するが内容が違う → User コピーへ退避:
      • 新 id = format!("{old_id}-user-edit")。これも既存と衝突するなら -2, -3 ... と採番
      • name = format!("{old_name} (edited)")。これも衝突なら (edited 2) 採番
      • origin: User { locked: false } で保存 (ユーザ編集物は最初は unlocked が安全)
    • id が seed sample ID と一致しない (純粋なユーザ作成) → そのまま origin: User { locked: false } で保存
  4. active_id の再写像: v1 の active_id が seed と完全一致なら seed 側の id へ、退避された場合は新 id へ、見つからなければ先頭 entry へ fallback。
  5. migration log を tracing::info! で残す (削除件数 / 退避件数 / active 再写像)。

起動時の URL hash 経路 (実行中 apply と分離)

実行中の URL hash 適用は §「Select と Apply を別 API として分離」のとおり active_locked() でガードするが、 起動時 (main.rs / startup.rs) は「URL に乗せた回路をアプリ起動と同時に開く」共有 URL の主用途を壊さないため、locked guard を通さない別経路として扱う。 ただし「locked My を URL 再読込で事実上上書きできる」抜け穴を塞ぐため、解決の優先順序を 4 段階で固定する。 

// startup.rs (pseudo)
fn boot_circuit(library: &mut CircuitLibrary, url_hash: Option<UrlPayload>) {
    let Some(payload) = url_hash else {
        // hash 無し → 最後に active だった entry を select
        return library.set_active(library.last_active_id());
    };

    // (1) URL payload が persisted active entry と完全一致なら active を維持。
    //     ページリロードで意図せず別 entry に切り替わらないため。
    if library.active_circuit_json() == payload.circuit_json {
        return; // 何もしない (active は既に正しい)
    }

    // (2) canonical sample と一致 → その Sample を select。新 entry は作らない。
    if let Some(sample_id) = library.find_canonical_sample(&payload.circuit_json) {
        return library.set_active(sample_id);
    }

    // (3) 既存 User entry のいずれかと完全一致 → その entry を select。
    //     User の locked / unlocked は問わず select 自体は guard 不要。
    //     これで locked My を URL から再読込しても entry の中身は触らず active 切替だけになる。
    if let Some(existing_id) = library.find_user_entry_with_json(&payload.circuit_json) {
        return library.set_active(existing_id);
    }

    // (4) どれにも一致しない URL → "current" 用 unlocked User entry を作成 / 上書きして active 化。
    //     ただし既存 "current" が locked になっているなら、それを保護して新 id を採番する。
    if library.entry_locked_by_id("current") {
        let fresh_id = library.fresh_id("current");
        library.create_user_entry(fresh_id.clone(), payload.circuit_json, /*locked=*/ false);
        library.set_active(fresh_id); // ← 作成と active 化は別ステップ。明示する。
    } else {
        library.set_active_current_circuit(payload.circuit_json);
        // ↑ 既存実装。origin: User { locked: false } の "current" entry を作る (or 上書き) + active 化を一括で行う。
    }
}
  • (1) active 維持: ページリロードで URL hash がそのまま残るので、同じ payload + 同じ active なら no-op にする。これで「locked My を見ていたユーザがリロードしたら別 entry に切り替わってしまう」事故を防ぐ。
  • (2) Sample 一致: 共有 URL の典型 (「友人が Bell state を共有」) は Sample select のみ、新 User を増やさない。
  • (3) User 一致: 「自分の locked 回路の URL を再共有 / 再読込」は、その entry の中身は触らず active 切替だけ。locked guard 不要、上書きも起きない。
  • (4) 新規 URL: どれにも一致しない場合のみ current 用の unlocked User を作る。既存 current が locked なら上書きせず新 id を採番して別 entry を作成 (locked 保護)。
  • 起動時の boot_circuit から呼ぶ helper はguard 不要、それ以外の経路から呼ぶ apply は必ず guard あり。

複製 (Duplicate) のルール

  • Sample / User どちらを複製しても、新 entry は origin: User { locked: false } で作成。lock は継承しない (新コピーは編集可能であるべき)。
  • name は既存ルール (「Name (copy)」→「Name (copy 2)」…) を踏襲。

「Select」と「Apply」を別 API として分離

現行は picker の select も URL hash の load も replace_editor_circuit() / apply_circuit_json() 経由でまとめて active entry の中身を書き換えている。 ここに単純な locked guard を入れると Example の select 自体が壊れる、入れないと URL から locked entry を上書きされる。 「editor へ読み込む helper」と「active entry を変更する guarded helper」を分けて、guard を後者にだけ付ける。 

impl QniApp {
    // ─── editor 読み込み helper (mutation 無し、guard 無し) ───
    /// 指定 entry の circuit_json から placed_gates / qubit_count を再構築するだけ。
    /// entry 自体は触らない。Example / locked My でも安全に呼べる。
    fn load_into_editor(&mut self, entry: &CircuitEntry, ctx: &egui::Context) { ... }

    // ─── active 切替 (entry の中身は触らない) ───
    /// picker からの select / 起動時 restore など。
    /// active_id を変更し、対象 entry を load_into_editor() で読み込む。
    /// entry の json を書き換えないので locked guard 不要。
    fn select_circuit_entry(&mut self, id: &CircuitId, ctx: &egui::Context) {
        self.library.set_active(id.clone());
        self.load_into_editor(self.library.active(), ctx);
    }

    // ─── active entry を更新する guarded helper ───
    /// editor の現在状態を active entry に commit。locked なら abort。
    /// 既存 commit_current_circuit() の guarded wrapper として配置。
    fn commit_active_if_unlocked(&mut self, ctx: &egui::Context) -> Result<()> {
        if self.library.active_locked() { return Err(LockedError); }
        self.commit_current_circuit_unchecked(ctx);
        Ok(())
    }

    /// URL hash や外部からの JSON を active entry へ適用 (実行中)。
    /// = circuit_json を上書きする mutation。locked なら abort + URL hash 巻き戻し。
    /// 起動時の経路は別 (§ 「起動時の URL hash 経路」)、ここを通さない。
    fn apply_url_payload(&mut self, json: String, ctx: &egui::Context) -> Result<()> {
        if self.library.active_locked() { return Err(LockedError); }
        self.replace_active_circuit_json_unchecked(json, ctx);
        Ok(())
    }
}

命名規約: mutation を起こす内部 helper には _unchecked 接尾辞を付け、外向き API は必ず guarded wrapper を経由させる。 commit_current_circuit() / replace_active_circuit_json() など既存呼び出しは commit_active_if_unlocked() / apply_url_payload() 経由に書き換える。

編集経路の guard 対象 entry は 2 種類ある (§ 04 実装ガードと対応): 

// active 編集系: active entry を guard
fn place_gate(&mut self, ...)        { if self.library.active_locked() { return; } ... }
fn remove_gate(&mut self, ...)       { if self.library.active_locked() { return; } ... }
fn clear_circuit(&mut self, ...)     { if self.library.active_locked() { return; } ... }
fn undo_circuit(&mut self, ...)      { if self.library.active_locked() { return; } ... }
fn redo_circuit(&mut self, ...)      { if self.library.active_locked() { return; } ... }
fn apply_url_payload(&mut self, ...) { if self.library.active_locked() { return Err(...); } ... }

// picker 行操作: 対象 entry id で guard (active と一致しないことがある)
fn rename(&mut self, entry_id: &CircuitId, new_name: &str) {
    if self.library.entry_locked_by_id(entry_id) { return; }
    self.library.rename_unchecked(entry_id, new_name);
}
fn delete(&mut self, entry_id: &CircuitId) {
    if self.library.entry_locked_by_id(entry_id) { return; }
    self.library.delete_unchecked(entry_id);
}

impl CircuitLibrary {
    pub fn entry_locked_by_id(&self, id: &CircuitId) -> bool {
        self.entries.iter().find(|e| &e.id == id).is_some_and(|e| match &e.origin {
            CircuitOrigin::Sample { .. } => true,
            CircuitOrigin::User { locked } => *locked,
        })
    }
}

submenu の Rename / Delete 項目を disabled 表示するだけでは不十分: UI race / 直接呼び出し (test / keyboard 操作) でも防ぐため、commit/delete API 側で必ず再チェックする。 duplicate / select / create_new / move_up / move_down / reorder / toggle_circuit_lock はガード対象外 (§ 04 参照)。 ただし toggle_circuit_lock は active が Sample のときAPI 側で no-op (match で Sample => return)。

icon_button() の API 拡張

現行 icon_button(ui, colors, icon, enabled, tooltip) に toggle 状態を渡すため、 ButtonState 構造体を導入して引数を統合する。 

pub(crate) struct ButtonState {
    pub enabled: bool,
    pub toggle_on: bool,   // active な toggle (例: lock が掛かっている)
}

fn icon_button(
    ui: &mut egui::Ui,
    colors: &Colors,
    icon: ToolbarIcon,
    state: ButtonState,
    tooltip: &'static str,
) -> egui::Response { ... }

show_edit_utilities 配置

Undo / Redo はもともと can_undo_circuit() / can_redo_circuit() で履歴有無を見ていた。 ここに「edit_allowed (= Example でない、かつ locked でない)」を AND 合成する。 Trash は履歴条件無しで edit_allowed のみ。Duplicate はガード対象外。 

// after Copy
let kind = self.library.active_kind();
let locked = self.library.active_locked();
let example = matches!(kind, CircuitKind::Example);
let edit_allowed = !example && !locked;

// Example または locked My では編集系を disable (§ 04 参照)。
// Undo / Redo は履歴条件と AND 合成。
icon_button(ui, colors, Undo,
    ButtonState { enabled: edit_allowed && self.can_undo_circuit(), toggle_on: false },
    "Undo");
icon_button(ui, colors, Redo,
    ButtonState { enabled: edit_allowed && self.can_redo_circuit(), toggle_on: false },
    "Redo");
icon_button(ui, colors, Trash,
    ButtonState { enabled: edit_allowed, toggle_on: false },
    "Clear circuit");

// Duplicate は常時 enabled (escape hatch)。
icon_button(ui, colors, Copy,
    ButtonState { enabled: true, toggle_on: false },
    "Duplicate circuit");

// Lock toggle。Example は固定 disabled、My は toggle_on で背景ピル。
let (icon, tooltip) = match (kind, locked) {
    (CircuitKind::My,      false) => (LockOpen, "Lock circuit"),
    (CircuitKind::My,      true)  => (Lock,     "Unlock circuit"),
    (CircuitKind::Example, _)     => (Lock,     "Locked (sample) — duplicate to edit"),
};
let lock_state = ButtonState { enabled: !example, toggle_on: locked };
if icon_button(ui, colors, icon, lock_state, tooltip).clicked() {
    self.toggle_circuit_lock(ctx);
}

toggle-on の背景ピル

icon_button() に「toggle-on かつ enabled なら背景を常時 colors.toolbar_hover_bg (= Flexoki ui) で塗る」分岐を足す。 アイコン色は tx-2 のまま、hover 時のみ背景を 1 段深い ui-2 に切り替え、icon を tx に。 新しい色トークン (accent_strong など) は導入しない。 

// icon_button() 抜粋 (toggle-on のとき)
if toggle_on && enabled {
    ui.painter().rect_filled(
        rect,
        egui::CornerRadius::same(6),
        if hovered { colors.line } else { colors.toolbar_hover_bg }, // ui-2 ↔ ui

}

シャックル弧の描画

既存 append_icon_arc() は 4 ステップで弧を近似する。 Lucide のシャックルは半径 5 / 約 180°〜270° の弧なので、ステップ数を 5〜6 に上げるかどうかは スナップショットテストで判断する。 paint_shackle_open は polyline (7,11)→(7,7) のあと半円弧 → 終端 (16.9, 6) で停止、 paint_shackle_closed は polyline + 半円弧 + 終端 (17, 7) → (17, 11) で閉じる。

Picker の section 化 (circuit_picker モジュール)

circuit_picker は現在 entries.iter().enumerate() の平坦 indexで drag / submenu / keyboard focus を扱っているが、Example / My の 2 セクションを描画するには 表示行モデルを section-aware に拡張する必要がある。 

enum DisplayRow {
    Header(SectionId),
    Entry { section: SectionId, entry_index: usize },
}
enum SectionId { Example, My }

fn build_display_rows(library: &CircuitLibrary) -> Vec<DisplayRow> {
    let mut rows = Vec::new();
    let examples = library.entries.iter().enumerate()
        .filter(|(_, e)| matches!(e.origin, CircuitOrigin::Sample { .. }));
    let users = library.entries.iter().enumerate()
        .filter(|(_, e)| matches!(e.origin, CircuitOrigin::User));
    // examples 先頭 → Header(Example) + Entry...
    // users 後 → Header(My) + Entry...
}

置換手順 (flat index → section-aware):

  1. 状態キーを usize 平坦 index から (SectionId, CircuitId) に置換。 DragState / PickerState::focused / submenu_index もこの組で持つ。build_display_rows() の Vec<DisplayRow> は描画専用に毎フレーム作る。
  2. drag 開始: DisplayRow::Entry { section, .. } の section が Example なら drag 開始しない。My のときだけ sameKindRows を section == My の Entry に限定して slot 計算 / splice。
  3. slot 計算とYクランプは Header の bounding rect を除外して My subset の Entry rect だけで行う (§ 01 のモック JS と同じ)。
  4. keyboard: ArrowUp/Down は DisplayRow::Header をスキップして前後の Entry へ。Home/End は active section の先頭/末尾 Entry。Tab は section 跨ぎ可。focused が Example だったとき lock toggle のキーは無視 (ToggleButton が Disabled なので Space/Enter で発火しない)。
  5. submenu: Move up / Move down は同じ section の subset 内 index で動く。My subset の先頭にいるなら Move up は disabled、末尾なら Move down は disabled。Example のときは Move up/down 項目自体を出さない。
  6. delete() / rename() など既存の usize index を取る API は CircuitId 引数版に書き換える。flat index は描画ヒットテストでのみ局所的に使う。

テスト計画 (受け入れ条件)

本 PR でカバーすべき自動テストの最小セット。受け入れ条件として CI に組み込む。 AGENTS.md の「1 テスト 1 アサーション」規約に従い、下記の各箇条書きは「観点 / シナリオの大分類」を示すもので、 実装時には 1 ケース 1 assert_* に分割すること (例: migration の 4 ケースは 4 つの #[test] 関数、 Playwright も test() 単位に 1 expect ずつ)。

  • migration unit tests (Rust, #[test] × 4 + v2 fallback 1 = 5):
    1. untouched seed 4 件のみ → v2 entries.len() == 4 を assert

    4. v1 read 失敗 (壊れた JSON) → seed のみで初期化されたことを assert
    v2 read/validate 失敗時の v1 fallback も別 #[test] として追加。
  • active_locked() 型不変条件 (Rust, tests/compile_fail/) — CircuitOrigin::Sample { locked: false } という直接構築がコンパイルエラーになることを trybuild で検証 (1 ファイル 1 case)。
  • Duplicate は常に unlocked (Rust, #[test] × 3) — Sample / locked My / unlocked My を duplicate した直後の新 entry を 1 アサーションずつ確認。
  • locked 中の編集拒否 (active 編集系) (Rust, #[test] × 6) — place_gate / remove_gate / clear_circuit / undo_circuit / redo_circuit / apply_url_payload をそれぞれ別テストで呼び、locked active entry の circuit_json が変わらないことを 1 つずつ assert (undo/redo は事前に履歴を積む setup を共有 fixture で)。
  • locked 中の編集拒否 (picker 行操作) (Rust, #[test] × 4) — active は unlocked My だが対象行は locked My / Sampleのケースを含めて:
    1. rename(locked_my_id, "new") → 対象 entry の name が変わらない
    2. rename(sample_id, "new") → 対象 entry の name が変わらない
