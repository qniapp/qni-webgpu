Spacer ゲート (空きスロット)

回路上に何も作用しない空きスロットを明示的に置くためのプレースホルダ。 見た目は 40 × 40 px の透明な当たり判定領域 + tx の 3 点だけで、 cyan-400 の角丸本体も、行列変換も、測定も持たない。列の間隔や例題回路の読みやすさを保つための視覚的な区切りとして扱う。

★ 批評 · 全体所見
「何もしないゲート」がそもそも「ゲート」として存在する根拠が薄い

H ページの全体所見と同じく、本仕様は Flexoki Light に厳密で、3 点だけの最小グリフ / 透明 hit 領域 / 回路 vs パレットの ホバー枠分岐などが根拠付きで書かれている。測定 / |0⟩ オペレーションと同じ「透明マーカ系」chrome の仲間として整理されている点もよい。

しかし Spacer は qni-webgpu のゲート群で最も特殊なケースで、§ 06 にあるように 「状態変化: linearize_ops が GateKind::Spacer を捨て、dispatch を発行しない」「外部 GPU 実行: Unsupported gate · Spacer として停止する」 という、量子計算上は純粋に no-op な要素である。仕様は「列を占有するだけで何もしない」ことを丁寧に書くが、 なぜこれを「ゲート」として持つ必要があるのか (空セルとは何が違うのか) という存在意義の核心が § 01 と § 06 のあいだに散在しており、「Spacer はそもそも存在すべきか?」という設計判断の根拠が弱い。

Quirk では Spacer は「列幅を保つための見える空白」として実装上の必要から生まれた要素で、回路を Quirk URL から シリアライズ / 復元するときに「空でないが何もしない列」を保持するために必要だった。qni-webgpu でも同じ理由なら、 その実装由来の経緯を § 00 前文として書いておくと、本ゲートが「ユーザに能動的に置いてもらう」のではなく 「Quirk 互換のために残す」性格のものだと正確に伝わる。

★ 批評 · Top Opportunities
影響度の大きい改善候補 (各論は本文中の批評ブロックに展開)
  1. 「ユーザに使われるか?」の UX 観点が欠如 — 何もしないゲートを palette から選んで配置する動機が明確でなく、UI 探索時に「これは何?」と誤クリックされる可能性 (§ 01 / § 04 参照)。
  2. 3 点 ("…") と三点リーダー (省略記号) の意味的衝突 — 「…」は一般 UI で「メニュー / 続きあり」を示す強い慣習がある。本仕様の 3 点は「空白」を意味するが、Quirk 互換の "…" シリアライズ ID もあり、用法と意味のズレが起きやすい (§ 02 参照)。
  3. tx (#100F0F = ほぼ黒) で 5 px 点を描く強さの正当性 — 「tx-2 では弱すぎ、tx なら見失わない」と書かれているが、「空白を示すマーカ」を本文と同じ濃さで描くのは矛盾する設計判断 (§ 02 参照)。
  4. § 06 「外部 GPU 実行で Unsupported gate · Spacer として停止する」が本ゲートの致命的欠陥 — qni-webgpu の二大実行経路の片方で動かないゲートを UI に置けることの是非が触れられていない (§ 06 参照)。
  5. § 04 のパレットホバー (内側 paper 枠) と回路ホバー (線だけ) の使い分けが H 系と非整合 — 透明マーカ系 4 ゲート (Spacer / Write0 / Write1 / Measurement) でホバー枠仕様の合議をしたい (§ 04 参照)。

§ 01概要 (見た目と用途)

Spacer は GateKind::Spacer、シリアライズ ID は Quirk 互換の "…" (三点リーダー 1 文字)。 パレットでは Gates section の 2 行目末尾に置かれ、ドラッグするとほかのゲートと同じ 56 px ピッチのスロットへ配置できる。 ただし、状態ベクトルには一切作用しないため、回路の意味論としては「列を占有する空白」に近い。

既定
透明領域 + 3 点
回路ホバー
purple-400 の線
パレットホバー
purple-400 + paper
ドラッグ
色変化なし

Spacer の役割は「見える空白」。通常の空セルは何も描かれず選択もできないが、Spacer は 3 点で存在を示し、ドラッグ / ホバー / 削除などの編集操作を受け付ける。

★ 批評 · § 01 概要
ユーザが palette から Spacer を能動的に選ぶ動機が薄い

本仕様は「列の間隔や例題回路の読みやすさを保つための視覚的な区切り」「3 点で存在を示し、ドラッグ / ホバー / 削除などの編集操作を受け付ける」 と Spacer の用途を書くが、ユーザが palette から Spacer を能動的に選ぶ動機を読者に伝える具体例がない。 H / X / CNOT を palette からドラッグするのは「回路を作る」という明確な目的があるが、Spacer をドラッグして何を達成したいのか (列幅を保つ? 読みやすさのため? Quirk URL の互換性のため?) が § 01 だけでは判別できない。

改善案: § 01 末尾に 「Spacer の使いどころ (具体例 3 つ)」を追加する: (a) 教科書例題の回路を再現するとき、Quirk から import した URL に Spacer が含まれていた場合 (b) 例題のコメント枠を空けたいとき (回路の "段落" を作る) (c) 制御線を伸ばしたいが、対象量子ビット側に何もゲートを置きたくないとき。 これがあれば、「ユーザに能動的に使ってもらう」or「Quirk 互換のためだけに残す」の方針も明確になる。

補足: § 01 mock では「① 既定 ② 回路ホバー ③ パレットホバー ④ ドラッグ」の 4 状態を 1 行に並べているが、 ③ パレットホバーだけ data-frame="palette" という別軸で、他の 3 つとは性質が違う (UI 状態 vs 文脈)。 Measurement § 04 と同型の問題で、状態モックの軸混在は本ファミリ共通の課題。

★ 批評 · § 02 配色
「空白マーカ」を tx (ほぼ黒) で描く強さ、および 3 点と一般 UI 慣習 (…) の衝突

tx (#100F0F) は本文や見出しと同じ最濃の文字色で、これを「空白を示すマーカ」に使う設計判断には 視覚的強さと意味の不一致がある。本文は「tx-2 では弱すぎ、tx なら 5 px 点でも見失わない」と 書くが、これは「空白を示す要素を、もっとも強い色で描く」という逆方向の判断。 Spacer が「他のゲートと並んだ時の 見える空白」だとすれば、視覚優先度は最低であるべきで、tx-3 (#B7B5AC) や ui (#E7E5DC) のように 背景と本体の中間色で描くほうが、意味と見た目が一致する。

加えて、3 点 ("…") は 一般 UI 慣習で「メニュー」「省略」「読み込み中」を強く意味する記号で、 Material Design / iOS / Bootstrap いずれも … = "more options" の意味で使う。 本仕様の Spacer は「空白」を示すが、palette でこれを見たユーザは「これはメニューゲート? 他のゲートが隠れている?」と 誤解する可能性が高い。Quirk 互換のシリアライズ ID も "…" (三点リーダー 1 文字) で、 Quirk の選択もまた一般 UI 慣習と衝突している。

改善案: 3 点をやめて "⌑" (square containing right) や "·" (中点 1 個) のような「空白」を強く示す記号にするか、 色を tx-3 まで落として「これは弱い視覚要素ですよ」と明示する。Quirk 互換 ID は維持しつつ、UI 上の見た目は qni-webgpu 独自に再定義する道もある。

★ 批評 · § 03 ジオメトリ
点の中心座標 (12, 24) / (24, 24) / (36, 24) から間隔 12 / 幅 6 を読者が暗算する必要がある

本仕様で「点の座標: x = 9 / 21 / 33、y = 21、width = height = 6」と書かれているが、 この値から「3 点の中心間隔 = 12 (viewBox 48 上)、実表示で 10 px」「3 点全体の合計幅 = 30 (実 25 px)、左右 7.5 / 7.5 px 余白」という Spacer の幾何関係は読者が暗算しないと出てこない。これは h-gate.html § 06 の「16 px 余白の内訳図がない」批評と同じパターンで、 計算済みの幾何関係を annotated diagram で見せると、設計の意図が一目で伝わる。

改善案: § 03 末尾に「点の幾何関係 (点幅 5 / 点間 5 / 余白 5 — 5 × 5 の対称配置)」のような等分構造を annotated diagram で示す。等分配置は Spacer が「幾何的にも空白の中央性を示す」要素であることを強調できる。

補足: geo-diagram SVG が他のページ (Write0 / Write1 / Measurement) と同じく 240 × 240 px サイズで、 中の SVG 内テキスト font-size="4" が実表示 12 px に相当する。これは Spacer 単独の問題ではないが、 本ファミリ全体で SVG 内テキストサイズの基準を統一したい (現状 4 / 3.6 が混在)。

§ 04状態バリアント

Spacer は本体色を持たないため、状態差はホバー枠とカーソルだけで伝える。 ドラッグ中も 3 点の色は変えず、「仮配置中」の紫色本体を出さない。

① 既定
tx の 3 点
② 回路ホバー
2 px stroke
③ パレットホバー
内側の空き
④ ドラッグ
色変化なし

パレット上だけ内側を paper で塗る。回路上で同じ処理をすると、透明ゲートの内部を通る wire や制御線を消してしまうため、回路上は線だけのホバー枠に統一する。

★ 批評 · § 04 状態バリアント
回路 vs パレットのホバー枠分岐が、透明マーカ系 4 ゲートで揃っていない可能性

本仕様は「回路ホバー = 2 px の線だけ / パレットホバー = 外側 purple + 内側 paper の二重枠」と書き分け、 実装も data-frame="palette" 属性で分岐させている。これは妥当な判断 (透明ゲートの内側を paper で塗ると、 回路上では wire や制御線を消してしまう) だが、同じく透明マーカ系の |0⟩ / |1⟩ オペレーションでは 「内側 bg ギャップなしの単線」を回路 / パレット問わず 統一して使い、Measurement は「パレットのホバーは外側 purple-400 + 内側 paper の二重枠、回路上のホバーは線だけ」と 分岐している。

結果として、透明マーカ系 4 ゲートで (a) Spacer / Measurement = 文脈分岐あり (b) Write0 / Write1 = 文脈分岐なし という非対称が生まれる。同族のゲートで仕様が分岐するのは、レビューと実装の両方で「このゲートはどっち?」を 毎回確認する負荷になる。

改善案: 透明マーカ系全 4 ゲートのホバー枠仕様を hover-frame.html に集約し、文脈分岐の有無を 1 か所で決める。 ホバー枠 primitive 仕様自体は既に存在するので、本ファミリ用のバリアント定義を追加する形で良い。

§ 05回路グリッド上の配置

Spacer は 1 本の量子ビットワイヤ上の単一スロットを占有する。空セルとは違い、3 点が表示されるため、列幅の確保や例題回路の視線誘導に使える。

うっすら入っている縦線は説明用のスロット境界。実 UI では wire と 3 点だけが見える。単独の Spacer はコネクタを作らず、span も伸びない。同じ列に Control / Anti-control がある場合は描画上の対象として縦コネクタに含まれるが、状態変化はない。

★ 批評 · § 05 回路グリッド配置
「Control / Anti-control がある場合は縦コネクタに含まれる」の重要仕様が note 末尾に隠れている

本章末尾の note に 「同じ列に Control / Anti-control がある場合は描画上の対象として縦コネクタに含まれるが、状態変化はない」と 重要な仕様が 1 文だけ書かれている。これは Spacer の意味論として「状態変化なし」と矛盾する微妙な仕様 (描画上は制御コネクタの対象 = ターゲットとして扱われるが、量子計算上は no-op) で、本ゲートの最も特異な振る舞いの 1 つ。 にもかかわらず、本文中で図解もなく、文章 1 文だけで通り過ぎている。

改善案: § 05 に 「制御コネクタに含まれた Spacer の挙動」の小見出しを設け、 slot-mock で「Control + Spacer + Spacer」の縦並びを実際に描く。これがあれば、 「Spacer は描画上は制御の対象になるが、measurement と違い後続列に影響しない」が一目で伝わる。 加えて、Quirk の "Identity gate" との関係 (Quirk の I ゲートが取り立てて何もしない場合の挙動) も 比較として書ければ、Spacer の存在意義がより明確になる。

§ 06意味論と実装契約

状態変化
ローカル WebGPU 実行では linearize_ops が GateKind::Spacer を捨て、dispatch を発行しない。
編集操作
配置・選択・削除・ドラッグは通常ゲートと同じ。空セルではなく、編集可能なプレースホルダとして扱う。
外部 GPU 実行
現状の Qiskit バックエンド経路では Unsupported gate · Spacer として停止する。
  • 3 点だけで描く: 空白を示す記号なので、操作ゲートの cyan-400 本体や枠線を足さない。
  • tx を使う: tx-2 では wire 上で弱すぎ、tx なら小さな 5 px 点でも見失わない。
  • wire マスクをしない: Spacer は回路の流れを止めない。wire が連続していることを保ち、点だけが上に乗る。
  • ドラッグ中に紫化しない: 本体 fill が無いゲートに purple-600 の仮本体を出すと、Spacer が操作ゲートに見えるため避ける。
  • span = 1 固定: 列を占有するだけで、複数量子ビットの領域を持たない。リサイズハンドルは出さない。
★ 批評 · § 06 意味論と実装契約
「外部 GPU 実行: Unsupported gate · Spacer として停止する」が Spacer の致命的欠陥

本章 semantic-grid 3 マス目に 「外部 GPU 実行: 現状の Qiskit バックエンド経路では Unsupported gate · Spacer として停止する」と 書かれている。これは CLAUDE.md によれば qni-webgpu の二大実行経路 (ローカル WebGPU / 外部 GPU = Qiskit バックエンド)の 片方で動かないことを意味する。ローカル経路では linearize_ops が Spacer を捨てて no-op になるが、 ユーザが Qiskit バックエンドに切り替えると同じ回路が突然動かなくなる。

この実装的非対称は Spacer の存在意義を根本から揺らがせる。ユーザが palette から Spacer をドラッグして配置し、 ローカル実行で問題なく動いたあと、Qiskit に切り替えると「Unsupported gate」エラーが出る、というシナリオが起きる。 改善案は 2 つ: (a) Qiskit バックエンドでも Spacer を no-op として扱うようバックエンド側を修正する、 または (b) Spacer を palette から外し、Quirk 互換のシリアライズ復元時にだけ「読むけど描かない」隠し要素にする。 現状の「palette には出るが、半分の経路で動かない」は最悪のユーザ体験。

補足: semantic-grid 3 マスのうち最後の「外部 GPU 実行」は、実装契約というより「このゲートは半分動かない」という 重要なユーザ警告。デザインシステム仕様で これを mini-card 1 つで済ませる扱いの軽さに違和感がある。 本ファイル冒頭の page-lede か、§ 01 概要に 「⚠ Qiskit バックエンドでは未対応」と 明示しないと、本仕様を読むユーザに警告が届かない。

補足 2: 5 項目の設計判断リストは h-gate.html / write0-gate.html と同じく「平等並び」問題を抱えており、 透明マーカ系共通 (cyan-400 を使わない / ホバー枠単線 / ドラッグ色変えない / wire マスクなし) と Spacer 単独 (3 点で描く / tx 色 / span = 1 固定 / Quirk 互換の no-op 性質) を階層化したい。
