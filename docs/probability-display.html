確率表示ブロック

任意の地点で span 内 量子ビットを測定した場合の各測定結果の確率を、 本体内に 横バー + XX.X% として可視化する確率表示ブロック (`表示ブロック` の定義は AGENTS.md 用語集と design-system §01 参照)。 状態ベクトルには影響しない。span は 1〜16 量子ビット (上限 16)、見た目は span 全体で同一視覚モデル。 本ドキュメントは描画仕様 (寸法 / 配色 / 挙動 / 実装参照) を 1 ヶ所にまとめたリファレンス。

§ 01 サイズ別の見た目 (1〜5, 16 量子ビット)

§ 02 パレットアイコン (ミニプレビュー)

パレットに並ぶ ProbabilityDisplay アイコンは 40 × 40 px の静的なミニプレビュー。 ガウシアン風の 4 行プレビュー (PROBABILITY_PREVIEW_BAR_WIDTHS = [0.30, 0.75, 0.55, 0.20]) で 「複数の測定結果を持つ確率分布ゲート」を表す。バー / 区切り / 外枠は本体と同じルール (区切り線はバー領域に引かない、外枠は ui-2 1 px、本体角ばり)。 ホバー時は外側のゲートホバー枠だけ表示 (行ホバー枠は出さない、静的なので行を選ぶ意味がない)。

§ 07 視覚要素

バー

  • 左から P(outcome k) × gate_w の幅で blue-200 を塗る
  • 右端 1 px は blue-400 の縦線で「確率境界」をマーク (Quirk と同じ流儀)
  • 各行は同じ高さで分割される (= 全体高 ÷ 2span)

行区切り線

  • 隣接 2 行のうち広いバーの右端から行右端まで ui-2 1 px を引く
  • バー領域では「色の境界」自体が区切りになるので線は引かない (Quirk と同じ流儀、視覚的に冗長な線を排除)
  • 計算式: x_start = rect.left() + rect.width() × max(prob[i−1], prob[i])、x_end = rect.right()
  • 高密度表示では省略する。実装上は row_h ≤ 2 px のとき行区切り線を描かず、Quirk と同じくバー / 対数ヒント線 / ホバー位置だけを残す

テキストラベル

  • 各行の右端から 2 px 内側に右詰めで XX.X% を描画
  • バー領域に重なる場合もテキスト色は変えない (色境界 two-tone なし)。blue-200 上の tx 黒で十分なコントラスト
  • 条件: row_count ≤ 16 && row_h > 8.0。満たさないときは描かない (代わりに § 08 の対数ヒント線を描く)

§ 08 対数ヒント線 (logarithm hints)

行高が小さい場合 (row_h ≤ 8 px、span 5 以上) は XX.X% ラベルを出せない。 代わりに各測定結果の確率を対数スケールの補助線として薄い灰色で描き、 線形バーでは見分けにくい 極めて小さい確率 の差を視覚的に残す。 Quirk の _paintMultiProbabilityDisplay_logarithmHints と同じ流儀。

発動条件

判定式 (qni-webgpu) showText = row_count ≤ 16 && row_h > 8
Quirk は textFits = row_h > 8 のみ。Probability5 (40 px 化後 row_h = 264/32 = 8.25) は Quirk ルールだとテキスト表示になるが、qni-webgpu は 9 px グリフより縦に詰まって読めないため row_count ≤ 16 も AND する。結果として Probability1〜4 のみテキスト、Probability5+ は対数ヒント線。
showText = trueXX.X% ラベルを描画。対数ヒント線は描かない (Probability1〜4)
showText = falseテキストを描かず、対数ヒント線を描画 (Probability5〜16)
線形バーとの重ね順対数ヒント線 → 線形バーの順で描き、バーの背後に補助線が残る (Quirk と同じ)

横位置の計算

スケール係数s = 1 / (4 + max(8, span))
横位置比x_ratio = clamp(0, 1, 1 + ln(p) × s) (ln は自然対数)
描画 xpx = rect.x + rect.w × x_ratio
境界挙動 p = 1 → x_ratio = 1 (右端) / p が小さいほど左へ寄る / p が極小または 0 なら clamp により x_ratio = 0 (左端) に潰れる
span 依存性 span が大きいほど s が小さくなり、ln(p) の効き目が緩やかになる (span = 8 → s = 1/12、span = 16 → s = 1/20)

描画形状 (連続ポリライン、Quirk 準拠)

  • 1 本の連続ポリラインで描く (Quirk の _paintMultiProbabilityDisplay_logarithmHints と同じ)。 各行の縦線 (px_i で長さ e = max(row_h, 1)) を、行境界で水平な接続線 (px_{i-1} → px_i) で繋ぐ。 全体として ECG / 階段状のシルエットになり、隣接行の確率差も視覚化される。
  • Path の構築: 
    beginPath()
moveTo(0, 0)
for i in 0..n:
  px = w × clamp(0, 1, 1 + ln(p[i]) × s)
  py = i × row_h
  lineTo(px, py)          // 前行 (px[i-1], py[i-1]+e) からの水平接続
  lineTo(px, py + e)      // 現行の縦線
lineTo(0, h)             // 左下に戻す
stroke()
  • 線スタイル: strokeStyle = tx-3 (#B7B5AC、視認性を確保するため Quirk の '#CCC' より濃い)、lineWidth = 1
  • Quirk 基準では行ごとに独立した縦線は不可。水平接続を省くと、密な span (5〜) で隣接確率の上下関係が読めなくなり、Quirk の見た目から逸脱する。現行シェーダは span ≥ 13 でも、事前集約した隣接 y ピクセル同士を水平接続して Quirk 基準を保つ

tooltip の log: ... dB との違い (重要)

行ホバー時の tooltip に出る log: (log10(p) × 10).toFixed(1) + " dB" は別仕様。 tooltip は 常用対数 (底 10) × 10 倍の dB 表示で、ユーザーへの数値情報提供が目的。 対数ヒント線は 自然対数 ベースでスケールした視覚的な補助線で、 数値そのものではなく「小さい確率同士の相対関係」を伝える。 両者は計算式 (ln vs log10) も用途 (描画 vs テキスト表示) も別。

qni-webgpu 現行実装

  • Probability1〜Probability4 (row_h > 8 px かつ row_count ≤ 16) は XX.X% ラベルのみ。対数ヒント線は描かない
  • Probability5〜Probability16 は対数ヒント線のみ。% ラベルは出さない
  • 本番経路で GPU → CPU readback しない。probability_output (= resources.probability.output_buffer) をフラグメントシェーダで probability_data としてバインドし、線形バーと対数ヒント線の両方を 1 パスで描く
  • シェーダ内で natural_log(p) と clamp(1.0 + ln_p * s, 0.0, 1.0) を計算 (s = 1.0 / (4.0 + max(8.0, f32(span))))
  • 連続ポリラインのシェーダ描画方針: フラグメントごとの判定で 「現在ピクセル (x, y) が ポリライン上か」を決める。具体的には row = floor(y / row_h)、log_x_cur = w × clamp(0, 1, 1 + ln(p[row]) × s)、 log_x_prev = (row > 0) なら w × clamp(0, 1, 1 + ln(p[row-1]) × s) を求め、 (a) 縦線: |x - log_x_cur| < 0.5 px もしくは (b) 水平接続: 行境界 (y_in_row < 1 px) かつ x が [min(log_x_prev, log_x_cur), max(log_x_prev, log_x_cur)] の範囲内 の場合に tx-3 を出力する。
  • span ≥ 13 (row_count > 4096) の集約描画: Probability13 以降は 1 ピクセル内に複数の測定結果が乗る (span 16 で 880/65536 ≈ 0.013 px/row、1 px あたり ~74 個の測定結果)。 PROBABILITY_AGGREGATE_SHADER が GPU 上で CSS y ピクセルごとの p_max = max(p[row_lo..=row_hi]) を probability_aggregate_rows に事前集約する。 フラグメントシェーダは probability_aggregate_data[slot, floor(local_y)] を読むだけで、 ピクセルごとの測定結果走査をしない。線形バー幅 (x_bar = w × p_max) と対数ヒント線の x 位置を 同じ代表値から決め、対数ヒント線は隣接 y ピクセルの代表値同士を水平接続する。
  • docs / コード内コメントでは「縦線」と呼ばず「対数ヒント線」または「対数スケールの補助線」と呼称統一する

§ 08.5 Quirk 高速化メモ

調査対象: ../oss/Quirk @ 8833791294e642795c8717038e84940a74b19a64。 16 量子ビット span の確率表示ブロックが高速に見える主因は、確率の算出とホバー描画を分離し、 ホバー中に重い確率計算やフラグメントごとの集約を繰り返さない構造にある。

Quirk の実装上の要点

  • 確率は表示ブロックの custom stat として一度だけ作る。 ProbabilityDisplay.js:48-64 の probabilityStatTexture は state texture を確率へ変換し、表示範囲のビットを寄せてから sumFoldFloat で対象外のビットを畳み込む。 CircuitComputeUtil.js:125-145 では、列ごとに必要な表示ブロックだけ customStatTexturesMaker を呼ぶ。つまり Probability16 の 65,536 個の確率は 「回路統計」の一部であり、ポインタホバーのたびに再計算しない。
  • 安定回路の統計をキャッシュする。 ui/sim.js:50-60 は回路定義が同じならキャッシュ済みの CircuitStats を返す。 ホバーは回路そのものを変えないので、main.js:143 の simulate(...) は 既存統計を使い回す。再描画は起きても、状態シミュレーションと Probability 確率集計は走らない。
  • CPU 側の描画は測定結果数に対して各 1 本の Canvas パス構築。 ProbabilityDisplay.js:146-170 のバー、173-195 の対数ヒント線は、 65,536 個の測定結果を lineTo でバー用パスと対数ヒント線用パスに積み、最後に fill() / stroke() する。 画面ピクセルごとに確率配列を走査しない。ブラウザの 2D Canvas ラスタライザに細い行の集約を任せる。
  • 高密度グリッドは早期に省略する。 ProbabilityDisplay.js:124-143 のグリッド描画は d = h / n < 1 のとき、 全区切り線を描かず薄い矩形塗りだけで戻る。Probability16 で 65,535 本の水平線を描かない。
  • ホバー固有の処理は 1 行分だけ。 ProbabilityDisplay.js:198-217 はポインタ位置から k = floor((pt.y - y) / d) を出し、 その 1 つの測定結果の p だけを読んで strokeRect と tooltip を描く。 マウス移動では全体の再描画自体は起きるが、重い確率統計はキャッシュ済みで、ホバー固有処理として全測定結果を走査しない。
  • 再描画要求を束ねる。 main.js:164-166 は再描画を CooldownThrottle に通し、 base/CooldownThrottle.js:18-20 / 52-74 の仕組みで短時間の連続要求を 1 回にまとめる。 ただし高速化の中核は再描画の間引きではなく、上記の統計キャッシュと Canvas パス描画。

qni-webgpu へ反映した方針

  • 本番経路の GPU → CPU リードバックは引き続き禁止。 Quirk は CircuitStats.js:359-364 で custom stats を CPU に読み戻して Canvas 描画するが、 qni-webgpu ではこの形をそのまま採らない。移植すべきなのは「再利用する統計 / 描画入力を前段で作る」構造であり、リードバックではない。
  • Probability16 をフラグメントシェーダのピクセルごとの集約で描き切らない。 span ≥ 13 はコンピュートシェーダで「画面 y ピクセルごとの代表値」を作り、描画パスは その小さいバッファを読むだけにした。これによりフラグメントごとの最大 ~74 個の測定結果走査を、ゲート高さぶんの事前集約へ移す。
  • ホバー固有の更新を小さくする。 ポインタが動いても状態シミュレーションと probability_output は再生成せず、ホバー中の測定結果とポップアップ値だけを差し替える。 現時点では y ピクセル代表値の集約パスを各描画準備で軽量に実行する。将来さらに詰める場合は、既存の step snapshot キャッシュと同じ発想で、circuit / slot / span / viewport 高さが変わるまで代表値バッファも再利用する。
  • 密な区切り線や装飾は描かない。 Quirk と同様、row_h < 1 では行区切りを捨て、バー / 対数ヒント線 / ホバー位置だけを残す。 見た目の情報量を保ちながら、描画プリミティブ数とフラグメント処理を抑える。

§ 10 ポップアップ仕様

行ホバー時に出るポップアップの常時表示版。実装と同じ CSS / マークアップを 静的に並べ、状態バリアントとアナトミーを Codex / 人間がスクロールだけで確認できるようにする。 ホバーを必要としないので、スクリーンショットレビューや diff レビューで仕様逸脱を検出しやすい。

Quirk オリジナル文言との差分

Quirk は 1 行タイトル Probability of |bin(k)⟩ (decimal k) if measured 形式だが、 qni-webgpu はタイポグラフィ階層を活かしてket を主見出し、サブテキストに自然文 + decimal を畳む形に再構成。 数値の意味 (raw % / log dB)・桁数 (4 桁 / 1 桁) は Quirk と完全互換だが、文言レイアウトは Quirk オリジナルから意図的に分かれる。 Quirk URL から import した回路でポップアップを出した場合も、qni-webgpu 側の本仕様 (ket + サブ + raw / log) が常に勝つ。

設計判断

  • ket を最大の主役にする: 「どの測定結果の確率を見ているか」がポップアップの最重要情報。14 px Geist Mono Regular で視覚的に最も強い
  • raw を 4 桁 / log を 1 桁にする: Quirk 互換 (toFixed(4) / toFixed(1))。raw は微小確率の比較、log は dB スケールの大まかな桁感を伝える
  • マイナス記号は U+2212 (−): hyphen-minus (-) より幅が広く、tabular-nums と同じ字幅に揃う
  • サブ・ラベルは tx-2: 当初 tx-3 を使ったが paper bg 上で読みにくかったため格上げ。tx-3 はポップアップ内では使わない
  • 角丸 6 px: Qni のゲート本体 (CornerRadius::same(6)) と同値にして UI 全体の調子を揃える。確率表示ブロックの本体は角ばりだがポップアップは別レイヤなので角丸でも齟齬なし
  • 枠 + soft shadow の二重表現: 枠 (ui-2 1 px) は paper bg との境界を明示、shadow は ≪浮いている≫ ことを示す。どちらか片方では弱い
  • span 16 でも 1 行で収まる: 16 bit ket = 16 文字、補足 30 文字程度。white-space: nowrap で折り返しを防ぐ (最大幅は ~280 px)

§ 11 リサイズハンドル

Probability は 1〜16、QFT / QFT† は現在の実行モード容量までの span をドラッグ変更するためのハンドル。ゲートの上下 2 ヶ所に出る purple-400 ベースのピル形 (24 × 6 px)。 通常は非表示で UI を圧迫せず、ゲートホバーで「奥から飛び出してくる」マイクロインタラクションを伴って出現。 ホバー枠 (§ 09 の 4 px purple-400 ring + 2 px paper gap) のさらに外側に 2 px の paper gap を挟んでレイアウトし、紫色を共有しながらも視覚的には明確に分離させる。

設計判断

  • 上下 2 個にする: span は両方向に変化させたいので、片側のみだと拡張方向が片寄って感じる。確率表示ブロック / QFT / QFT† は同じ「縦方向に伸びる回路要素」なので、上下対称な配置に統一する
  • 4 px ring の外側 + 2 px gap で配置: ホバー枠とハンドルはどちらも purple-400 なので、隣接させると 1 つの大きな図形に見えてしまい「リングの一部?」と誤認される。2 px の paper gap で明確に別オブジェクトと分離
  • purple-400 → purple-600 で深さの変化: ハンドルが「触れる対象 → 操作対象」に遷移したことを色濃度で示す。彩度ではなく明度の変化なので、認知負荷が低い
  • バウンスするイージング: 線形 / ease-out だと「現れる」だけだが、オーバーシュートを伴うイージングは「主張する」表現になる。ゲートに span を変える機能があることを目立たせるための意図的な誇張
  • scale(0.7) → 1.0 → 1.15 → 1.25 の連続スケール: 1 軸の連続変化なので状態遷移が自然に読める。サイズ差は +15 %, +25 % と明確に体感できる程度。10 % 以下だとほぼ気づかない
  • 形状はピル (capsule): 矩形だと「点」、円だと「ボタン」、ピルだと「つまみ」に読める。span を 引き伸ばす動作とピル形の横長が一致して、操作のメタファとして馴染む
  • ハンドル幅 24 px はゲート幅 40 px より狭い: ゲート横中央に小さめに配置することで「ゲートの一部」感を出しつつ、左右にゲートの縁が見える
  • cursor: ns-resize: 「上下方向にドラッグできる」を OS のカーソル変化でも伝える (ハンドルの形だけに頼らない)

§ 12 URL シリアライズ (Quirk 互換)

確率表示ブロックの シリアライズ ID は Quirk と同じ語彙を採用する (Quirk URL インポート / 双方向の URL 共有のため)。 ただし下記の #circuit=... 形式は Quirk オリジナルの URL hash 構造であり、qni-webgpu 現行の URL 表現 (/#<percent-encoded JSON>) とは hash 内のキー名・構造が異なる。 本セクションは Quirk URL の語彙互換性を示すための参考であり、qni-webgpu 内部の URL 設計は別仕様 (TBD)。

spanserialized id
1"Probability"
2..16"Probability2" .. "Probability16"

URL fragment 内では JSON 生のまま:

#circuit={"cols":[["Probability"]]}                 # span 1、q0 に 1 個
#circuit={"cols":[["Probability3"]]}                # span 3、q0..q2 に
#circuit={"cols":[[1,"Probability3"]]}              # span 3、q1 起点 (q0 placeholder)
#circuit={"cols":[["H","H","H"],["Probability3"]]}  # H × 3 → Probability3

percent-encode 済み (%7B"cols"%3A%5B%5B"Probability"%5D%5D%7D) も等価に parse できるようにする (Quirk と同じ挙動)。Quirk 側ロジックは ProbabilityDisplay.js:280, 294 参照。

§ 13 GPU バックエンド経路

qni-webgpu は 2 つの GPU バックエンドを持つ: ブラウザローカルの WebGPU と、リモートの Qiskit GPU。 確率表示ブロックの確率取得はバックエンドごとに別経路だが、本体描画 (§ 04〜§ 11) は完全に共通。 ここでは「描画シェーダに渡す probability_data をどう得るか」だけをバックエンド別に規定する。

バックエンド共通の制約

  • span 上限 = 16。回路全体が 32 量子ビットであっても、1 つの確率表示ブロックが見る測定結果は 216 = 65 536 が上限
  • full statevector / full probabilities は受け取らない。32 量子ビット 回路で全状態 = 232 = 約 4.3 G 個の測定結果を転送 / 保持しないため。確率表示ブロックは常に marginalize 済みの表示ブロックごとの probabilities のみを扱う
  • CPU リードバック不可 (WebGPU 経路)。Qiskit GPU 経路は性質上 JSON で返ってくるので CPU を経由するが、その場合も probability_data として GPU バッファに 1 回 アップロードしたあとは描画完結
  • nesting 禁止: バックエンド種別に関わらず Probability の中に Probability は置けない (Quirk と同じ、§ 03 概要参照)

WebGPU ローカルバックエンド

確率計算各確率表示ブロックごとに PROBABILITY_REDUCE_SHADER (compute) を発行。状態ベクトルを span 内 量子ビットについて marginalize
出力先probability_output (resources.probability.output_buffer) の各 Probability スロット (params.output_slot 単位、MAX_PROBABILITY_OUTCOMES = 65 536 ストライド)
描画同じバッファを PROBABILITY_RENDER_SHADER に probability_data としてバインドし、フラグメントシェーダで直接サンプル。CPU リードバックなし
同期compute → render はキューレベルで順序通り、明示的な fence は不要

Qiskit GPU バックエンド (リモート)

確率計算 回路送信時に各確率表示ブロックの位置と span を解析し、確率表示ブロックごとに save_probabilities(qubits=[...], label="probability:<gate_id>") または save_probabilities_dict(...) を Qiskit circuit に挿入する。
full statevector / full probabilities (save_statevector / save_probabilities() 引数なし) は挿入しない
レスポンス形式 バックエンドは確率表示ブロックごとの marginalized probabilities のみを返す: 
{
  "probability": [
    { "gate_id": "", "span": 3, "probabilities": [p_0, p_1, ..., p_7] },
    { "gate_id": "", "span": 5, "probabilities": [p_0, ..., p_31] },
    ...
  ]
}
probabilities 長は 2span、合計 ≤ 1.0、p_k は |bin(k)⟩ の確率。 big-endian order は WebGPU 経路と一致 (§ 03 「測定結果」行参照)
GPU アップロード受信した各 probabilities 配列を probability_output の対応スロットに 1 度 queue.writeBuffer でアップロード。以降の描画は WebGPU 経路と完全同一
更新タイミング1 回路実行 = 1 レスポンス。確率表示ブロックの値はそのレスポンス到着時点でアトミックに全て更新される
未対応 / エラーバックエンドが古くて save_probabilities を返さない場合は確率表示ブロック全行を NaN 扱いで描く (Quirk 互換、Quirk の printParagraph("NaN", ...) と同じ流儀)

32 量子ビット 回路での挙動 (重要)

  • 回路 量子ビット数が 32 であっても、確率表示ブロック 1 個が見るのは最大 16 量子ビット (span ≤ 16)。残り 16 量子ビットは marginalize で消える
  • 32 量子ビット 回路に Probability16 を 4 個並べることは可能。各 Probability は独立に 216 = 65 536 個の測定結果の probability vector を持つ
  • Qiskit バックエンドに送るとき、save_probabilities(qubits=[q_start..q_start+span-1]) として、Probability が span するレジスタだけ抜き出す
  • WebGPU バックエンドで 32 量子ビットを扱う場合は、状態ベクトルが 232 複素数 = 32 GiB となり通常端末では不可。32 量子ビット 級は Qiskit バックエンド限定 (これは確率表示ブロック仕様外、回路全体の制約)
