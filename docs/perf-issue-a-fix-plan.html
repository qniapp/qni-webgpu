§01 「encoder を外に出すだけ」では済まない理由

最初に思いつくのは「create_command_encoder をループの外に出して、最後に 1 回 submit するだけ」という案。残念ながらこれだと壊れる。

WebGPU の仕様上、queue.write_buffer はすべての submitted command buffer の前にまとめて実行される。つまり同じ buffer を上書きすると、最後の値ですべての dispatch が読み取りに行く。

Fig. 1   単純に encoder を外出ししただけだと、param の上書きで全 dispatch が同じ値を読む → 結果が壊れる。

§02 解決策 — copy_buffer_to_buffer

ポイントは「params の更新も encoder の中で行う」こと。queue.write_buffer ではなく encoder.copy_buffer_to_buffer を使えば、param 更新と dispatch を encoder 内で順序保証つきで交互に並べられる。

Fig. 2   staging buffer に全 gate の params を一括 upload → encoder 内で copy_buffer_to_buffer を挟みながら dispatch → 最後に 1 回 submit。
なぜ copy_buffer_to_buffer か

bind group のレイアウト変更が不要で、既存コードへの影響が最小。動的オフセット (has_dynamic_offset) を使う方法もあるが、shader の binding 定義から触る必要があり diff が大きくなる。性能差は小バッファでは無視できる。

§03 実装ステップ

  1. StateVectorResources に staging buffer を 4 種追加

    gpu.rs:783–1798 (StateVectorResources::new)

    SimulationOp の各 variant ぶん、上限サイズの staging buffer を作る: 

    const MAX_OPS: usize = 256; // 回路の最大ゲート数 + 余裕

gate_params_staging:           create_buffer(MAX_OPS * size_of::<GateParams>())
bloch_params_staging:          create_buffer(MAX_OPS * size_of::<BlochParams>())
measure_reduce_params_staging: create_buffer(MAX_OPS * size_of::<MeasureReduceParams>())
measure_collapse_params_staging:create_buffer(MAX_OPS * size_of::<MeasureCollapseParams>())

    usage は BufferUsages::COPY_SRC | COPY_DST。各 staging は uniform alignment を意識してパディング (256 byte 境界)。

  2. 事前パスで params を分類して staging に packing

    新規ヘルパー関数 — gpu.rs StateVectorCallback::prepare 内

    dispatch ループに入る前に、sim_ops を 1 周して op 種別ごとに Vec<GateParams> などへ分け、それぞれ queue.write_buffer で staging に一括 upload する。 

    let mut gate_packed: Vec<GateParams> = Vec::with_capacity(sim_ops.len());
let mut bloch_packed: Vec<BlochParams> = Vec::with_capacity(sim_ops.len());
// ...
for op in &self.sim_ops { /* 振り分け + slot index 記録 */ }
queue.write_buffer(&gate_params_staging, 0, bytemuck::cast_slice(&gate_packed));
// 4 種ぶん同様

    副産物として、各 op がどの staging slot を使うかの index 列ができる。これを次のステップで使う。

  3. encoder をループの外に出す

    gpu.rs:2126 直前

    recompute ブロック先頭で encoder を 1 つだけ作る: 

    let mut encoder = device.create_command_encoder(&wgpu::CommandEncoderDescriptor {
    label: Some("recompute_batched_encoder"),
});

  4. ループ内: copy_buffer_to_buffer + dispatch

    gpu.rs:2126–2289 (各 match arm)

    各 op の処理を以下の形に書き換える (ApplyGate の例): 

    let slot_offset = (gate_idx * GATE_PARAMS_STRIDE) as wgpu::BufferAddress;
encoder.copy_buffer_to_buffer(
    &resources.gate_params_staging, slot_offset,
    &resources.gate_params_buffer,  0,
    size_of::<GateParams>() as wgpu::BufferAddress,
);
{
    let mut pass = encoder.begin_compute_pass(&...);
    pass.set_pipeline(&resources.compute_pipeline);
    pass.set_bind_group(0, &resources.compute_bind_groups[in_index], &[]);
    pass.dispatch_workgroups(dispatch_x, 1, 1);
}
// queue.submit はしない

    CaptureBloch / MeasureReduceSample / MeasureCollapse も同形に。

  5. ループ後: 1 回だけ submit

    gpu.rs:2289 直後
    queue.submit(Some(encoder.finish()));

  6. 関連: write_buffer の重複削除

    gpu.rs:2132 / 2174 / 2219 / 2261 (旧コード)

    各 match arm にあった queue.write_buffer(&resources.gate_params_buffer, ...) 系の行はすべて削除。staging に置き換わっている。

  7. テスト harness の確認

    apps/egui-web/tests/ + read_*_impl

    read_state_vector_impl など test-only readback API は production submit 経路と独立しているので、振る舞いは変わらないはず。それでも E2E テストで結果が一致することを確認。

§04 計測 — Before/After を数字で見る

推測ではなく実測で効果を確認する。最低でも以下 3 点を取る:

  • Chrome DevTools の Performance パネルで recompute 中の queue.submit 呼び出し回数 (Console / Performance イベント) を Before/After で比較
  • WebGPU timestamp queries (wgpu::QuerySet::Timestamp) で recompute の壁時計を計測。30 ゲート回路で recompute ワンショットを N 回繰り返し中央値を取る
  • ドラッグ中のフレーム時間 — 既存の egui-web-drag-profiling.md のメソドロジに沿って frame time を取り、引っかかりが消えるか確認
注意

Chromium の chrome://flags/#enable-webgpu-developer-features を有効にしないと timestamp queries が使えないことがある。Playwright で計測するときは launch options に --enable-features=WebGPUDeveloperFeatures を渡す。

§06 リスク評価

● Low

順序の崩れ

WebGPU は同一 encoder 内の copy / pass を発行順に実行することを仕様で保証。memory barrier も自動挿入。

● Medium

staging サイズの上限

MAX_OPS を超える長大な回路で OOB。debug_assert!(gate_idx < MAX_OPS) を入れて早期に検出。実用上は 256 で十分。

● Low

uniform alignment

各 slot を 256 byte 境界にパディング。min_uniform_buffer_offset_alignment を Limits から動的に取って計算するのが安全。

● Low

copy のオーバーヘッド

16–64 byte の intra-encoder copy は driver 上ほぼ無料。submit 集約のメリットが圧倒的に上回る。

● Medium

初回 staging 作成の追加メモリ

MAX_OPS × 256B × 4 種 ≈ 256KB の追加 GPU メモリ。回路を開いている間は常駐。許容範囲。

● Low

roll back 容易性

1 PR 内に閉じる変更。問題が出れば revert で元に戻せる。
